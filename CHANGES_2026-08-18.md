## 1. Fix: "Noida" flashing in the home-page location chip

### Symptom reported

Arriving at the home page — by tab switch, by back button, or after
pull-to-refresh — showed `Noida / 110003` for a fraction of a second before
correcting itself to the actually-selected address.

### Root cause

Three layers stacked into one visible bug.

1. `_buildLocationInfo` fell back to `users.area` / `users.pincode` whenever
   `browsingAddressProvider` returned null. Those columns held legacy,
   unvalidated free text — the reported row had `area = 'Noida'` with
   `pincode = '110003'`, a Delhi PIN. Nothing had ever validated the pair.
2. `_initializeData()` used `ref.invalidate(userAddressesProvider(userId))`,
   which recreates the notifier in `AsyncValue.loading()`.
   `browsingAddressProvider` resolves the stored id against that list with
   `whenOrNull(data:)`, so it returned null for the whole refetch window.
3. `main_wrapper.dart` used `body: screens[currentIndex]` with no
   `IndexedStack`, so every tab switch **destroyed** `HomePage`. Coming back
   re-ran `initState` → `_initializeData()` → step 2 again. The back button hit
   the same path, because `PopScope` just sets the index to 0.

`_lastKnownLocation` could not cushion it either: it is State, destroyed with
the widget.

### What changed

- The `users.area`/`users.pincode` fallback is **gone**. No browsing address
  now shows `'Select delivery location'`. A neutral placeholder beats
  confidently wrong data.
- `_initializeData()` calls `userAddressesProvider(userId).notifier.refresh()`
  instead of `invalidate`, so the list never passes through a loading state.
  The redundant `activeAddressProvider` invalidate was dropped (it is derived).
- `main_wrapper.dart` is now a **lazy `IndexedStack`** — tabs are preserved,
  unvisited tabs stay placeholders so app start doesn't build all five screens.
- Because home now stays alive, `initState` no longer fires per visit, so a
  `ref.listenManual(navigationIndexProvider, …)` re-runs `_initializeData()`
  when the Home tab becomes active again, preserving the old refresh-on-return
  behaviour.

### Side effects worth knowing

Tabs now keep scroll position and state, and long-lived streams (e.g. the
wallet listener) stay open once a tab has been visited rather than being torn
down on every switch.

## 2. Change: "Default" vs "Selected" address are now distinct in the UI

### The problem

`ManageAddressesScreen` drove its green border and elevation from
`address.isDefault`, so tapping a different address moved the home-page header
but left the highlight on the default — the screen gave no indication of which
address was actually driving the session. The checkout picker
(`select_address_page.dart`) already showed a separate green "Selected" chip,
so the two screens disagreed about how to present the same two concepts.

Worse, the card tap was `onAddressSelected != null ? … : null`, and
`settings_page.dart` / `navigation_helper.dart` construct the screen without
that callback — so **tapping a card from Settings did nothing at all**.

### What changed

- Border/elevation and a green "Selected" chip now follow
  `browsingAddressIdProvider`; the "Default" badge stays independent on
  `is_default`. Both can render at once.
- The name/type row moved into `Expanded`/`Flexible` with ellipsis, so a long
  name can't push two badges off-screen.
- Card taps always work, write only the browsing address, and a new
  `popOnSelect` flag decides whether to pop (home: yes; Settings: no, so the
  highlight visibly moves in place).
- "Set as Default" no longer silently drags the browsing address with it.

### The two concepts, for reference

| | Stored in | Scope | Read by |
|---|---|---|---|
| **Default** | `addresses.is_default` | Account, all devices | Admin ad-hoc order/subscription preselect, fallback for browsing address |
| **Browsing** | `SharedPreferences`, `browsing_address_id_<userId>` | Device, per user | Home chip, catalogue serviceability, cart, checkout init |

## 3. Fix: the notification toggle was decorative

### Symptom reported

`users.notifications_enabled = false` in the database, yet push notifications
still arrived on a device with permission granted.

### Root cause

Two independent problems.

- **The column was never read at send time.** A grep of the whole repo found
  `notifications_enabled` only in `schema.sql`, `claim_adhoc_user`'s insert
  defaults, migration `009`'s grant list, `settings_page.dart` and
  `user_model.dart`. The actual send path — admin `notificationService.ts` →
  `send-notification` edge function → `device_tokens` → FCM — never consulted
  it. `sendToAll` literally selects every distinct `user_id` from
  `device_tokens`.
- **The switch lied on open.** It initialised to `true` and loaded
  asynchronously, so it rendered ON before flipping to OFF — and if the read
  threw, it stayed ON, showing the opposite of the stored value.

### What changed

- `Hetha_admin/services/notificationService.ts` — `sendNotification` now
  filters target user ids by `notifications_enabled` before invoking the edge
  function. One choke point, so `sendToAll`, order-delivered, wallet-debited
  and low-balance all inherit it. Two deliberate calls: the **in-app inbox row
  is still written for everyone** (the setting is labelled "Push
  Notifications", not "hide notifications"), and if the preference lookup
  itself errors it **fails open** and pushes, because silently dropping a
  low-balance warning is worse than an unwanted push.
- `settings_page.dart` — the switch is disabled with a "Loading…" subtitle
  until the stored value is read, and toggling now also
  registers/unregisters the FCM device token.

### Observed behaviour afterwards

Turning the toggle off makes the admin panel report "No target users found".
That message comes from `app/api/admin/notifications/route.ts:32`, which checks
`device_tokens` **before** the new preference filter is ever reached — the
token row is gone, so there is nothing to look up. Both layers agree, via the
more direct of the two mechanisms.

## 4. Database: migration `018` — drop four dead `users` columns

Applied live and confirmed. `users.area`, `users.pincode`, `users.dark_mode`
and `users.language` are gone.

### Why

- **`area` / `pincode`** — denormalised copies written once by the admin panel
  at customer creation and never kept in sync with the customer's real
  addresses. Serviceability, cutoffs and delivery frequency all resolve from
  the *address* pincode via `pincodes` → `delivery_areas`. These were also
  actively harmful: they were the source of the flash in §1.
- **`dark_mode` / `language`** — write-only. The settings screen stored them;
  nothing ever read them back. `Hetha_app` ships no `ThemeMode` and no
  `localizationsDelegates`/`supportedLocales`, so both were permanently inert.

### Verification done before writing the migration

Because no `psql`/Supabase CLI and no Postgres connection string are available
locally (only REST keys), two independent routes were used:

- **Live PostgREST OpenAPI schema** (read-only, service role, no table data
  fetched): confirmed the live `users` column list matched `schema.sql`
  exactly, that only `users` exposed `area`/`dark_mode`/`language`, and that
  the live RPC list matched `functions.sql` (the sole difference being
  `set_reviews_updated_at`, a trigger function PostgREST cannot expose) — so
  the function snapshot was current and grepping its bodies was trustworthy.
- **In-process Postgres (PGlite)**: loaded `schema.sql`, `functions.sql`,
  `policies.sql`, `indexes.sql` and all 17 migrations, then queried the
  catalog. **No** tracked dependency on the four columns (no index,
  constraint, default, generated column or RLS policy), **no** trigger on
  `public.users` at all, and the drops succeeded individually and together
  without `CASCADE`.

Two dependencies that Postgres would *not* have warned about, since plpgsql
bodies are not tracked:

1. `claim_adhoc_user` names `dark_mode` and `language` in its `INSERT` — it is
   recreated by the migration.
2. Migration `009`'s `GRANT UPDATE (…)` list names `area` and `pincode`.

The three other body matches were false positives:
`internal.place_order_core` (`v_address.pincode` → `orders.pincode`),
`internal.create_subscription_core` (`p_address->>'pincode'` → lookup in
`public.pincodes`), and `update_address_as_default` (updates
`public.addresses`).

### The migration

`docs/db/migrations/018_drop_legacy_user_columns.sql`, wrapped in
`BEGIN`/`COMMIT`:

1. **Pre-flight guard** — walks `pg_depend`/`pg_rewrite` for any view
   referencing the four columns and aborts *naming it*, rather than failing
   with Postgres' generic "other objects depend on it". This existed for the
   one thing that could not be verified offline: `v_active_subscriptions` and
   `v_subscription_demand` exist live but were created in Studio, so their
   definitions are not in the repo, and `v_active_subscriptions` demonstrably
   joins `users` (it exposes `customer_name`/`customer_phone`).
2. **`claim_adhoc_user` recreated** without `dark_mode`/`language`, *before*
   the drop, so the live function is never referencing missing columns.
3. **`DROP COLUMN IF EXISTS` ×4, no `CASCADE`** — deliberately, so anything the
   guard missed fails loudly instead of being silently deleted.
4. **Restated column-level `GRANT UPDATE`**, with `wallet_balance` still
   absent.

### Migration `009` made replay-safe

Its literal `GRANT UPDATE (…)` column list was replaced with a `DO` block that
grants only the columns that currently exist. This matters more than it looks:
`009` **revokes the table-level grant first**, so once the literal list failed
on a post-`018` schema, the whole statement aborted and left
`wallet_balance` writable. The money-integrity suite caught exactly that when
the snapshots were briefly edited ahead of the migration.

### Outcome

Live `users` is now `id, email, phone, first_name, last_name, wallet_balance,
notifications_enabled, created_at, updated_at, is_adhoc`. Re-reading the live
PostgREST schema after applying confirmed all four gone, all ten survivors
present, `claim_adhoc_user` still callable, and **both views still exposed** —
so neither had depended on the columns and the guard never had to fire.

### `idx` is not a column

The `"idx": 4` seen in a pasted row is the SQL client's row number.
`schema.sql` has no such column and the live schema confirms it.

### Also removed

- `Hetha_app/lib/services/user_area_service.dart` — dead file, nothing imported
  it. Its own header documented this deprecation ("replaces the redundant area
  field that was previously stored in user documents").
- The `users.pincode, area` fallback in `subscription_page.dart`.
- Language + Dark Mode tiles, state and helpers from `settings_page.dart`.
- The four fields from `UserModel`.
- `area`/`pincode`/`dark_mode`/`language` writes in
  `customerService.createCustomer`, the Area/Pincode inputs in
  `AddCustomerForm.tsx`, and `language`/`dark_mode` from `lib/types.ts`.

### New permanent test

`docs/db/tests/verify_018_drop_legacy_user_columns.mjs` (`npm run verify:018`)
— 10 checks in in-process Postgres: columns gone, idempotent re-run,
`wallet_balance` still closed while `first_name`/`notifications_enabled` stay
writable, **both** `claim_adhoc_user` branches (re-key an existing ad-hoc row
preserving its wallet balance / insert a new row), and the dependent-view
guard firing against a synthetic view.

## 5. Fix: cart writes were failing silently

### Symptom reported

Add milk ×5 and a second product; everything looks right until pull-to-refresh,
after which **only the first-added milk remains, at quantity 1**, and all other
products are gone.

### Root cause

`cart_items` has a `UNIQUE` index on `(user_id, variant_id)`
(`uq_cart_user_variant`) while its primary key is `id`. `upsert(rows)` with no
`onConflict` makes PostgREST resolve against the **primary key**, and the
payload carries no `id` — so every write was an `INSERT` of a fresh row, which
then violated the unique index (`23505`).

Two things turned that into total data loss:

- **The error was swallowed** by `catch (e) { logDebug(…) }`, and
  `CartNotifier` updates state optimistically *before* writing — so a failed
  write was indistinguishable from a successful one until the next read.
- **All items ship in one batch**, so a single conflicting row aborted the whole
  statement. Adding a *new* product in the same write therefore saved nothing.

Sequence: milk added (insert succeeds, DB = milk 1) → milk raised to 5
(violation, whole call fails) → second product added, batch `[milk=5, other=1]`
(milk still violates, entire batch rejected) → refresh reveals DB = milk 1.

This predates the write-ordering fix in `3f77613`; that commit correctly
serialized calls that were already failing.

### What changed

- `upsert(cartItems, onConflict: 'user_id,variant_id')` — a real `UPDATE`.
- `updateCart` no longer swallows failures; it throws.
- `_enqueueWrite` keeps the queue future itself resolved (a rejected one would
  break every write chained after it) but now calls `fetchCart()` to reconcile
  and **then** sets `errorMessage` — order matters, because `fetchCart()`
  clears it. The cart page already listens on that, so a failed write now
  shows a SnackBar and snaps back to the saved cart instead of leaving a
  phantom quantity.

## 6. Change: out-of-stock items are now actually removed from the cart

### The problem

An out-of-stock line was only *flagged* (`isInStock: false`) and left in the
cart, while the notice claimed it "has been removed from your cart". Two
consequences:

- **The notice never appeared.** `fetchCart` populated `removedItems`, but the
  cart page listens on `outOfStockItems`, which `fetchCart` never set.
- **The row kept feeding the delivery charge.** The charge is weight-tiered, so
  a heavy out-of-stock item inflated the displayed total — which feeds
  checkout's wallet affordability check.

### What changed

`fetchCart` splits out-of-stock lines out of state and deletes them through the
existing write queue (so the delete cannot race a concurrent add), preserving
the surviving quantities. `outOfStockItems` is now populated, so the user is
actually told.

### Safety

`in_stock` comes from the server on the same read, and `CartService` returns an
empty envelope on error — so a failed or partial fetch yields nothing to
delete. "Everything vanished, remove it all" is the dangerous misreading and
there is a test pinning it. The out-of-stock visual treatment stays and is
still reachable, because `product_details._addToCart` passes `isInStock` from
the product, so a locally-added out-of-stock item shows flagged until the next
fetch clears it.

**Accepted tradeoff:** if `products.in_stock` is ever flipped false by mistake,
the customer's cart line is deleted on their next refresh rather than greyed.
This was chosen over the alternative (keep the row, show "not available,
please remove to continue") after explicitly weighing both.

## 7. Feature: undeliverable items are flagged in the cart

### The gap

The cart page had no awareness of the browsing address. An item that could not
be delivered there looked completely normal — full colour, counted in the
subtotal. The problem surfaced only one screen later, in checkout, as a text
list of names in a warning banner.

### What changed

- `CartItem` gains `deliveryScope` (+ `isLocalOnly`), read from the `products`
  join `cart_service` already fetches — **no extra query**.
- `cart_page` greys out any local-only item while the selected address is
  non-serviceable: a luminance `ColorFilter` on the thumbnail, a "Not
  deliverable here" badge, and the details column dimmed so the row reads as
  inactive while scrolling. This reuses the existing out-of-stock visual
  language rather than inventing a new one; out-of-stock keeps visual priority
  when both apply.
- **Unlike out-of-stock, quantity and remove controls stay active** — an
  undeliverable item is resolvable by switching address or removing it, so
  locking the controls would trap the user.

### Two latent bugs fixed while wiring it

`product_details_page._addToCart` and `allproducts_page._addToCart` both
construct `CartItem` directly from a `ProductModel` and were **not** passing
`deliveryScope` — so any local-only product added from those screens would have
defaulted to `'all_india'` and never been flagged.

## 8. Fix: cart and checkout now agree on deliverability and totals

Four related inconsistencies, some of them newly created by §7.

### 8.1 Checkout's address change updates the browsing address

It previously wrote only `_checkoutAddress`, a field on the page State — so
`SelectAddressPage(fromCheckout: true)` returned early before any persistence,
and **neither** `is_default` **nor** the browsing address moved. Consequences:
the cart's greyscale, the catalogue filter and the home chip kept using the old
address (two screens, two verdicts, same cart), and the choice evaporated on
leaving the page, since checkout re-initialises `_checkoutAddress` from the
browsing address.

`is_default` is still deliberately untouched — that is the account-wide primary
the admin panel preselects for staff-placed orders, so shipping one order
elsewhere must not move it.

### 8.2 A "Remove this/these item(s)" button in checkout's banner

The banner has always said *"Remove them to continue, or switch to a
serviceable address"* while offering only the second remedy — the cart rows in
checkout are display-only, so "remove them" meant backing out to the cart, which
the screen never said. Fixing it needed product **ids**, not just the names the
banner prints, so `_undeliverableProductIds` is captured alongside them. No
confirmation dialog, matching the cart's own delete button.

### 8.3 The cart blocks Check Out when *any* item is undeliverable

The cart blocked only when *every* item was undeliverable, while checkout blocks
on *any* — so a cart of "deliverable + local-only" under a non-serviceable
address was waved through into a screen that then refused to proceed. An
explanatory line now sits above the disabled button, because a greyed-out button
with no stated reason is the same dead end in a different place.

### 8.4 Money derives from the orderable lines only

Both screens quoted the delivery charge over the **entire** cart
(`cartSignature(cartState.items)`); `cartSignature` filters only empty
`variantId` and `quantity > 0`. Because the charge is weight-tiered, an
undeliverable line added its weight and inflated the displayed total — and that
total feeds `walletRequired = subscriptionReserve + orderTotal`, so a customer
could be told *"Short by ₹X, recharge or pay online"* for an order their wallet
actually covered. Refusing money you could have taken is worse than a wrong
label, and it is silent.

Subtotal had a third rule again: `CartNotifier` excluded out-of-stock but not
undeliverable.

Cart and checkout now derive subtotal, item count and the delivery quote from
the same orderable set, and `_placeOrder` sends only those lines instead of
relying on the server to reject the rest. Undeliverable rows are still shown,
greyed; they just stop contributing to the money. When nothing is orderable the
placeholder fee is ₹0 rather than flashing ₹50 for a delivery that isn't
happening.

Checkout filters on `_undeliverableProductIds` — from the authoritative
`products` read — rather than the cart row's cached `deliveryScope`, since it is
the blocking money path and a row hydrated before that field existed would
default to `'all_india'`.

### Structural change

The shared rules moved to **`lib/utils/cart_rules.dart`**
(`isCartItemUndeliverable`, `orderableCartItems`, `cartItemsSubtotal`,
`cartItemsCount`, `canCheckOutCart`). Checkout needed `cartItemsSubtotal`, and a
screen importing another screen for business rules is exactly the coupling that
let these two drift apart.

### The server was never at risk

`internal.place_order_core` rejects the order outright if the address pincode is
non-serviceable and any cart item is `delivery_scope = 'local'` (migration
`016`), and `internal.normalize_cart` rejects anything inactive or out of stock.
The delivery charge is computed server-side by
`internal.compute_delivery_charge`. All of §8.4 was a **display** correctness
problem with a real user-facing consequence, not a money-integrity hole.

## Decisions considered and rejected

- **Remove `is_default` and keep only the selected address.** Rejected. The
  admin panel depends on it: `CreateOrderModal.tsx:44` and
  `CreateSubModal.tsx:41` preselect
  `addresses.find(a => a.is_default) || addresses[0]` when staff create ad-hoc
  orders/subscriptions, and the browsing address lives in `SharedPreferences`
  on the customer's phone — invisible to admin. `customerService.ts:121` also
  sorts `is_default DESC`. Without it, staff would guess among up to 5
  addresses, and a fresh install would fall back to "first by `created_at
  DESC`" — the most recently *added* address. Collapsing the two concepts in
  the **UI** (tap = select = default) remains a viable future option and was
  discussed; the schema should stay either way.
- **Remove the address-change option from checkout.** Rejected. It is
  currently the only in-place remedy when the browsing address is
  non-serviceable; removing it would leave Place Order disabled with a banner
  naming two remedies and offering neither. The real defect was the divergence,
  fixed in §8.1.
- **Clear the cart when the address changes.** Rejected. Hostile for a prepaid
  wallet grocery app with recurring subscriptions, and there is no
  data-integrity reason — the server re-validates at order time.
- **Auto-remove undeliverable items on address change.** Rejected — silent
  deletion without a decision. (Out-of-stock auto-removal in §6 *was* chosen,
  explicitly, as a separate call.)
- **A warning banner in the cart** (the first proposal). Superseded by the
  per-item greyscale in §7, which points at the specific row instead of making
  the user cross-reference a list of names against a scrolling cart, and costs
  less code by slotting into the existing `isInStock` pattern.
- **Switching checkout's deliverability check to `CartItem.deliveryScope`.**
  Rejected. It is the blocking money path and should stay authoritative.
