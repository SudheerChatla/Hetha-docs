## 1. Pause and start dates were off by one day

`services/dailyOps/generateRunSheet.ts` compared database `date` values with
`new Date(...)` against the target day's IST midnight. `new Date('2026-11-10')`
is 00:00 UTC, which is 05:30 IST, so it falls *after* the IST midnight of the
same day. Every "on or after" check was therefore one day late:

| Rule | Before | Now |
|---|---|---|
| First day of a pause | delivered and charged | paused |
| Subscription start date | skipped; first delivery a day late | delivered |
| New item's start date | item missing that day | included |
| Last day of a pause, end date, day after | correct | unchanged |

The customer app stores pauses as the plain calendar day
(`pause_service.dart`) and the subscription start date as the picked day, so
there was no workaround on the app side hiding this.

**Fix:** the dates are compared as `YYYY-MM-DD` strings. Two helpers were added
to `lib/deliverySchedule.ts`: `toYmd` and `isWithinDays`.

**Effect on live customers once deployed:**
- A new subscription's first delivery is on its start date, not the day after.
- A pause covers its first day.

## 2. Regenerating after an unlock could charge twice

After a super-admin unlock, the day's orders are un-finalized but stay `paid`
(the wallet was debited at finalize). Generate's cleanup deleted every
un-finalized pending order without looking at the payment, then recreated it
as `pending`, so the next finalize debited the customer again.

**Fix:**
- `generateRunSheet.ts`: the cleanup keeps any order whose `payment_status` is
  not `pending` (`paid`, `failed`, `refunded`).
- `app/api/admin/daily-ops/route.ts`: `generate` now refuses a finalized or
  reconciled date on the server (409). Before, only the button in the browser
  was disabled.

This is a stopgap. Edits made after an unlock are still not settled (an added
item is not charged, a removed item is not refunded); that needs the
charge-by-difference work in the open items.

## 3. One cut-off rule for subscriptions (migration 036)

To deliver on a given morning, ops must know the order by the evening before
(`delivery_areas.order_cutoff_time`). One-time orders already followed that in
the database (migration 033). Subscriptions did not:

- **New subscription:** the app always offered "tomorrow" as the earliest
  start, at any hour, and the database stored whatever it was sent.
- **Run sheet:** the only cut-off check was in `generateRunSheet.ts`. It built
  the cut-off in the server's timezone (UTC on Vercel), so a 16:30 cut-off was
  applied as 22:00 IST two days before delivery, and the customer was never
  told the start had moved.
- **Day edits:** "no changes to tomorrow after the cut-off" was enforced by
  the app only, using the phone's clock.
- **Pauses:** `upsert_pauses` / `remove_paused_dates` (what the app calls)
  checked ownership only, so a customer could pause or un-pause tomorrow at
  any hour. The table also accepts a customer's direct insert.

**The rule, now in one place** (`internal.earliest_change_date`): the earliest
day a customer can start a subscription, or change, pause or resume a day, is **tomorrow
in India time, or the day after once the area's cut-off time has passed**. An
area with no cut-off time always gives tomorrow.

| Where | Change |
|---|---|
| Database: `create_subscription` | For customers, a start date that is too early (or missing) is moved forward to the earliest day. Item start dates are never before the subscription start. Admin callers are not restricted. |
| Database: `modify_daily_order`, `modify_daily_orders_bulk`, `revert_daily_order` | Customers cannot change a day before the earliest day. Today is always closed; tomorrow closes at the cut-off. A bulk edit with one closed day is refused whole. Admins with `subscriptions:edit` bypass. |
| Database: `upsert_pauses`, `remove_paused_dates` | Customers cannot pause or un-pause a day before the earliest day. Days in a range that are already paused are ignored, so extending a pause still works. A refused request changes nothing. Admins bypass. |
| Database: trigger on `subscription_pauses` | A customer's direct insert (not through the two functions) cannot start before the earliest day. The app does not use that path. |
| Database: `get_earliest_subscription_start(pincode)` | New, read-only, for the app's date picker. |
| Admin: `generateRunSheet.ts` | Its own cut-off check is removed; the start date now carries the decision. |
| App: create-subscription screen | The date picker's first day comes from the database. If the cut-off passes while the screen is open, Subscribe shows the new start date and asks the customer to confirm. If the lookup fails, the picker falls back to tomorrow. |
| App: subscription calendar | A pause or resume the database refuses now shows the database's sentence ("The delivery on 12 Nov 2026 can no longer be paused...") instead of a raw error. |

**Old app builds keep working:** a too-early start date is moved forward, not
rejected. Their "Starting <date>" message can then be one day early, only when
a cut-off time is set and has passed.

**Nothing changes for customers today**, because no area has a cut-off time.
The rule starts applying when one is set in Delivery Areas → Edit Area.

**One behaviour change that applies even with no cut-off time set:** a
customer can no longer pause, resume or edit **today's** delivery, or pause a
past day, through the database. The app's calendar already blocked today for
edits.

**Rollout order:**
1. Paste `036_subscription_cutoff_rule.sql` into the Supabase SQL Editor and
   run the verification queries at the bottom of the file.
2. Deploy the admin panel (push `Hetha_admin` `main`).
3. Release the app.

The admin and app changes are safe to ship before the migration while no
cut-off time is set; the app's lookup fails quietly and falls back to tomorrow.
