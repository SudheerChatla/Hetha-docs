# CHANGES — 2026-08-30

Session driven by tester feedback from the Hetha group. Six issues were reported
after a testing round; each was checked against the source before any change was
made. Five turned out to be real defects with identifiable root causes, one was a
design question rather than a bug, and investigating them surfaced three further
problems the testers had not reported.

Every fix below was verified with `flutter analyze` (clean) and the test suite
(**56 passing**, up from 29 — 27 new tests added).

---

## Customer App (Hetha_app)

### 1. Notification inbox showed every time 5h30m early

**Reported:** "Incorrect time was shown in the notifications section."

**Root cause:** not the formatter — the column type. `notifications.created_at`
was declared `timestamp without time zone`, so PostgREST serialised it with no
`Z` and no offset (`"2026-08-27T16:15:00"`). Dart's `DateTime.parse` reads an
offset-less string as **local** time, so an already-UTC instant was shifted by
the device's offset. In IST that is 5h30m, which matches the reports exactly.

The same class of bug had already been hit on the wallet page, which carried a
local workaround (append `Z` when no offset is present) that was never
generalised — `wallet_transactions.created_at` has the identical declaration.
`device_tokens`, defined a few lines below `notifications` in the schema, was
correctly `timestamp with time zone`, which is what made the inconsistency easy
to miss.

**Fix (two layers):**
- Migration `019_timestamptz_user_facing.sql` converts the three affected
  columns to `timestamptz` (see backend section).
- New `lib/utils/date_utils.dart` provides `parseServerTimestampToLocal()`,
  which assumes UTC when a string carries no offset. This keeps clients correct
  against a database where the migration has not been applied yet, and stops a
  future column added with the wrong type from silently reintroducing the bug.

Its offset detection deliberately only inspects the portion after the `T`/space
separator, so the hyphens in `2026-08-27` are not mistaken for a negative UTC
offset — the trap a naive `contains('-')` check falls into. Pinned by a test.

The notifications page and the wallet page now share this helper, removing the
duplicated inline workaround. `_formatTime` also now tolerates a null/malformed
value and clamps a negative age (device/server clock skew) to "Just now"
instead of rendering a negative duration.

**Files:** `lib/utils/date_utils.dart` (new),
`lib/screens/notifications/notifications_page.dart`,
`lib/screens/wallet/walletpage.dart`

### 2. Adding an address was slower than every other address operation

**Reported:** "When adding a new address it takes a bit more time compared to the
remaining operations."

**Root cause:** request count, not network luck. A single add performed up to
**four sequential round trips**:

1. `getUserAddresses()` — a full list fetch used only to learn whether the list
   was empty
2. `_clearOtherDefaults()`
3. the actual `insert().select().single()`
4. `refresh()` from the provider afterwards — another full list fetch

By comparison `updateAddress` costs one or two. That 2–4× difference is what the
testers were feeling.

**Fix:**
- The emptiness check is now a count-only query (`select('id').limit(1).count()`)
  that transfers no rows, and is skipped entirely when the address is already
  flagged default, since the answer cannot change the outcome.
- `_clearOtherDefaults` is skipped for a user's first address — there is nothing
  to clear, so the request was pure latency.
- `UserAddressesNotifier.addAddress` no longer refetches. The insert already
  returned the persisted row, so it is spliced into local state at the front
  (matching `getUserAddresses`' `created_at desc` ordering). When the new address
  becomes the default, the previous default is demoted locally too, so the UI
  cannot briefly show two "Default" badges.
- If no list is loaded yet (cold start, or a previous error), it falls back to a
  full `refresh()` rather than leaving state holding one orphaned row.

**Files:** `lib/services/address_service.dart`, `lib/providers/address_provider.dart`

### 3. "Place Order" could be submitted twice on wallet / COD

**Reported (partly):** "When placing the order, before the confirmation, if I
suddenly come back the order is being placed but the cart stays as it is."

**Root cause:** `_isPaying` — the flag that disables the submit button — was set
**only** inside `_startRazorpayPayment`. On the wallet and COD paths,
`placeOrderTransaction` was awaited with no guard at all, so the button stayed
live for the entire duration of the request. A double tap, or backgrounding and
returning mid-flight, could fire `_placeOrder` a second time.

**Fix:** added `_isPlacingOrder` for the wallet/COD path and an `_isSubmitting`
getter combining both flags. The button and the undeliverable-items action both
read `_isSubmitting`, and `_placeOrder` opens with an `if (_isSubmitting) return;`
re-entrancy guard — disabling a button is not instantaneous, and an
already-dispatched tap can still run before the rebuild. The flag is released
only on failure; on success the page pops, and re-enabling a control on a dying
route would reopen the same window during the pop animation.

**Note:** this addresses duplicate *submission*. It is a client-side guard only —
`placeOrderTransaction` has no verified idempotency key, so a network-level retry
is not covered. Worth revisiting server-side.

**Files:** `lib/screens/checkout/checkout.dart`

### 4. A paid Razorpay order left the cart full and gave no confirmation

**Reported:** after paying online, returning to the app while the spinner was up
resulted in a correctly placed order visible in Orders — but the cart still held
the items and no success message ever appeared.

**Root cause:** the success handler cleared the cart *after* the verification
await:

```dart
await ref.read(cartNotifierProvider.notifier).clearCart();
```

`cartNotifierProvider` is global and survives navigation, but **`ref` does not** —
it belongs to the checkout page's `State`. Leaving checkout during verification
disposed that State, so when the edge function returned, `ref.read` threw. The
throw was caught by the handler's own `catch`, where `mounted` is false, so
**nothing ran**. The order was already placed (the edge function had completed
server-side), but the cart was never cleared and neither the success nor the
failure message was ever shown.

This only affected the Razorpay path because it has a verification window long
enough to navigate away from; the wallet path completes too quickly to hit it.
The critical part is that the *failure* branch was silenced the same way —
"Payment received but order failed, contact support with payment ID …" is the
worst possible message to lose.

**Fix (three layers):**
- The notifier is captured **before** the await and used afterwards, so cart
  clearing no longer depends on the widget being alive.
- New root `MyApp.scaffoldMessengerKey` wired into `MaterialApp` (mirroring the
  existing `navigatorKey` pattern). `ScaffoldMessenger.of(context)` needs a live
  context, so a popped page cannot report anything; outcomes now surface wherever
  the user actually is.
- `PopScope(canPop: !_isSubmitting)` plus a disabled back arrow keep the user on
  the page until verification resolves, with an explanatory message on attempted
  exit. The completion path is robust either way, but seeing the spinner resolve
  into a result beats wondering whether the payment landed.

Also added the `logDebug` that this failure path previously lacked entirely.

**Not covered:** if the app is killed *before* `verify-order-payment` is invoked,
Razorpay holds the payment and no order exists. That needs server-side
reconciliation against `payment_intents` and cannot be fixed client-side.
Deferred deliberately.

**Files:** `lib/screens/checkout/checkout.dart`, `lib/main.dart`

### 5. Orders list reloaded twice, and blanked to a skeleton on every refresh

**Reported:** "When the order is marked as delivered and the user is on the
orders page, there is a double reload."

**Root cause (two separate problems):**

*The doubling:* two independent triggers both called `_scheduleRefresh()` — the
Realtime `postgres_changes` subscription, and an FCM push listener. One admin
action fires both, at unrelated latencies. With a 400ms debounce each won its own
window, producing two refreshes.

*The visible flash — the more important one:* `_loadOrders()` assigned a fresh
`Future` and the `FutureBuilder` returned `OrdersPageSkeleton()` for
`ConnectionState.waiting`. So **every** refresh blanked the whole list and rebuilt
it. That flash was what testers actually saw as a "reload"; the duplicate trigger
just made it happen twice.

**Fix:**
- The push listener was removed. It was a leftover from the 2026-07-02
  "Push-Triggered Auto-Refresh (Zero Realtime Connections)" design, superseded
  for orders on 2026-08-24. Realtime is strictly more reliable here: it is a
  WebSocket authenticated by JWT and filtered by RLS, and works regardless of
  notification permission (verified: `orders` and `order_tracking` are both in
  the `supabase_realtime` publication, and `policies.sql` grants
  `Users can read own orders` on `auth.uid() = user_id`).
- The page now retains the last successful list and renders it while a refetch is
  in flight. The skeleton appears only on a genuine first load, so an admin
  status change updates rows in place with no blink. A failed *background*
  refresh keeps the visible data instead of replacing it with an error screen;
  only a user-initiated pull-to-refresh surfaces a message.
- Debounce returned to **400ms** (from the 1200ms stopgap), so updates now land
  faster than they originally did while showing no flicker.
- The empty state was wrapped in a `RefreshIndicator`, since a first load that
  legitimately returned nothing previously had no way to retry.

**Replacing the removed fallback:** `postgres_changes` never replays events missed
while disconnected, so a status change made while the app is backgrounded is
invisible to a still-mounted screen. That gap — not notification permission — was
the only thing the push listener genuinely covered. It is now handled by a
lifecycle refresh on resume, gated by `ResumeRefreshPolicy`.

The gate matters: Flutter reports a lifecycle change for pulling down the
notification shade, the app switcher, permission dialogs, incoming calls and
screenshots. Refreshing on every resume would fire constantly. The threshold is
**20 seconds**, chosen to sit just under the realtime client's heartbeat interval
(`realtime_client-2.7.3/lib/src/constants.dart` →
`defaultHeartbeatIntervalMs = 25000`): within one heartbeat the socket has not had
the chance to notice a problem, so it is almost certainly still connected.

`ResumeRefreshPolicy` was extracted into `lib/utils/` rather than inlined,
because the widget is private and `OrderService` is not injectable — inline, the
rule would have been untestable. With an injectable clock it now has 9 tests
covering the boundary, the `inactive → hidden → paused` sequence not restarting
the clock, and duplicate resume callbacks not double-firing.

This threshold is a deliberate heuristic: a socket that drops during a brief
background would be missed until the next refresh or pull. Judged acceptable
against refetching on every glance away — and it is one constant in one place.

**Files:** `lib/screens/orders/order_page.dart`,
`lib/utils/resume_refresh_policy.dart` (new)

### 6. A user's first address was not auto-selected

**Reported:** "If there is only one address it should be both selected and
default, but the very first time I need to manually select it."

**Root cause:** `BrowsingAddressNotifier._init()` runs exactly once, at provider
construction. For a user with no addresses it correctly resolved to `null` — and
nothing ever re-ran it. Adding a first address created it with `is_default = true`
in the database (`AddressService.addAddress` handles that correctly), but the
browsing-address state stayed `null`, so the home-page chip and everything else
driven by it showed nothing selected. Only the zero→one transition was affected;
by the time a second address is added, state is already non-null.

**Fix:** the notifier now keeps a `ref.listen` on the address list and adopts the
default (or first) address whenever the list becomes non-empty while nothing is
selected, persisting it so the choice survives a restart exactly as a manual
selection would. An `_initialised` flag prevents it racing `_init`'s own
resolution, and an explicit stored selection is never overridden. `invalidate()`
was refactored onto the same `_preferredAddressId` precedence helper so the two
paths cannot drift.

**Files:** `lib/providers/browsing_address_provider.dart`

### 7. Home calendar card changed size when there were no subscriptions

**Reported separately during the session.**

**Root cause:** the empty and loading states of the home calendar card had
padding but no height, so each collapsed to fit its own content (~112px and
~146px) while the populated card is 160px of calendar strip plus its footer row
(~190px). The result was a visibly smaller box and up to two layout jumps as
state resolved, shifting everything below it.

**Fix:** introduced `_calendarPageHeight` (160, previously hardcoded on the
`PageView`), `_calendarFooterHeight` (30) and `_calendarCardHeight` as their sum,
and pinned all three states to it. The populated card's footer is now a
fixed-height `SizedBox` too, so the states agree **by construction** — change the
strip height later and all three move together instead of silently drifting.

The empty state's message is vertically centred (in a ~190px box, leaving it at
the top looked stranded); the loading shimmer stays top-aligned so it sits
exactly where the real calendar strip appears and does not seem to shift when
data arrives.

**Files:** `lib/screens/home/home_page.dart`

### 8. Notification event system: dead code removed

Prompted by the question of whether the push-refresh mechanism was still needed
at all after orders moved to Realtime. It **is** still needed — by exactly one
consumer — so the stream stays, but most of it was dead:

| Removed | Why it was dead |
|---------|-----------------|
| `NotificationEvent.lowBalance` | never emitted by anything |
| `NotificationEvent.subscriptionUpdate` | never emitted; `subscription_page` filtered on it, so that branch could never be true |
| `NotificationEvent.walletDebited` | emitted, but nothing listened — the wallet screen self-updates via its own `.stream()` on `users` |
| `NotificationEvent.general` | emitted on every push, nothing listened — the bell badge uses a separate `_badgeController` refreshed by `_refreshBadgeCount()` |

`_routeToEvent` now returns `NotificationEvent?` and both handlers publish only
when non-null, so no-op events never reach the stream. The enum went from five
values to one.

**Kept, because it is live:** `NotificationEvent.orderDelivered` and the
`onNotificationEvent` stream — the **subscription calendar** listens to it and
has no Realtime subscription of its own (the only Realtime in the app is the
orders channel and `user_service.dart`'s `.stream()` on `users`). Deleting the
stream would have silently stopped the calendar updating live. The badge stream
is also untouched.

**Possible follow-up:** giving the subscription calendar a Realtime channel on
`subscription_daily_orders` (already in the publication) would remove the last
listener and allow the whole event system to go. Tradeoff: `CHANGES_2026-08-24.md`
§2 reduced channel count deliberately because Supabase's quota counts channels
per user, so this is not a free win — worth checking whether it can ride the
existing channel.

**Files:** `lib/services/notification_service.dart`,
`lib/screens/subscription/subscription_page.dart`

### Not a bug: subscription product selection UI

**Reported:** "With four products subscribing is fine, but if more products
become subscribable we need a better UI approach."

Investigated and **left unchanged**. The groundwork is already in place:
`create_subscription_page.dart` has cursor-based pagination (20/page), debounced
search, and a `defaultSub`/`additionalSub` split already enforced ("select at
least one default product"). Nothing is broken — this is a product design
decision, not a defect.

Directions worth prototyping rather than continuing to search for a single
answer: grouping by category with collapsible sections, a "frequently
subscribed" / recommended-combo shelf, or a two-step category → items flow
instead of one long list.

## Shared backend (docs)

### Migration 019 — timezone-aware user-facing timestamps

`docs/db/migrations/019_timestamptz_user_facing.sql`, **applied and verified**.

Converts to `timestamptz`:
- `notifications.created_at`
- `notifications.sent_at`
- `wallet_transactions.created_at`

Safe by construction: these columns are written by `now()` under a session whose
TimeZone is UTC (Supabase default), so stored wall-clock values are already UTC
and `AT TIME ZONE 'UTC'` reinterprets them without moving any instant. Defaults
are re-set to `now()` after the type change. The conversion takes an
`ACCESS EXCLUSIVE` lock for the duration of the table rewrite, so it was run
off-peak. `idx_notifications_user_created` is rebuilt automatically.

Verified post-apply via `information_schema.columns` — all three report
`timestamp with time zone`.

`notifications.read_at` and the `device_tokens` timestamps were already correct
and left alone.

**Note:** 31 `timestamp without time zone` columns remain in the schema. Only the
three that feed user-visible timestamps were converted; the rest are not
displayed and a wider change carries a much larger blast radius. Worth a separate
pass for consistency.

**Snapshots synced** to match reality: `docs/db/schema.sql`,
`Hetha_app/doc-schema/schema.sql`, `Hetha_admin/docs/schema.sql` — all three had
drifted.

## Admin Panel (Hetha_admin)

**No code changes.** Two findings:

**1. Admin had the same timestamp bug, and migration 019 fixed it too.**
`app/admin/customers/[id]/page.tsx` and `app/admin/payments/TransactionTable.tsx`
render wallet timestamps with `new Date(txn.created_at)`. JavaScript also treats
an offset-less date-time string as local time, so admin was displaying wallet and
payment times 5h30m early — the same bug, unreported. Now correct with no code
change. Worth spot-checking a customer's wallet history.

**2. Nothing breaks from the wire-format change.** Checked:
`services/notificationService.ts` writes `sent_at` as
`new Date().toISOString()` (carries `Z`, already stored as UTC — unaffected);
cursor pagination on `created_at` compares values obtained from the same source,
so it stays self-consistent.

**Pre-existing issue noted, not changed:** `app/api/admin/dashboard/route.ts`
computes "today" as `new Date().toISOString().split('T')[0]` — the **UTC** date.
Between 00:00 and 05:30 IST that is still yesterday, so the dashboard's
today-credits figure can be wrong during the early-morning delivery window.
Unrelated to this migration and unchanged by it, but flagged because operations
run in exactly that window.
