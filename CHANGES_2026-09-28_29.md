## 2. Editing a single day's order failed with an RLS error (42501)

**Reported:** after creating a subscription, changing a day's quantities and
tapping **Save Changes** showed `new row violates row-level security policy
for table "subscription_daily_orders" (42501)`.

**Root cause:** the app wrote `subscription_daily_orders` /
`subscription_daily_order_items` directly from the client. Migration 009 made
those tables admin-write-only — correctly, because `unit_price` /
`total_value` are what the daily run sheet bills against, so a customer must
never write them.

**Fix (long-term, same pattern as `place_order` / `create_subscription`):**

- **Migration 022** (`docs/db/migrations/022_customer_daily_order_rpcs.sql`, applied ✅):
  - New column `subscription_daily_orders.is_customer_modified`.
  - `public.modify_daily_order(user, subscription, date, items)` —
    `SECURITY DEFINER`. Checks ownership, refuses past / finalized / paid /
    non-pending days, prices every line from `product_variants` (client price
    ignored), applies the 3-day wallet buffer when the edit raises the day's
    cost, and replaces that day's order atomically, flagged
    `is_customer_modified = true`.
  - `public.revert_daily_order(user, date)` — "Reset to Default"; removes the
    pending customer edit so the default is regenerated.
- **App** (`f9e68e8`): `saveDailyOrder` / `deleteDailyOrder` now call these RPCs
  and send only `{variant_id, quantity}`. Removed the unused `totalValue`
  parameter.
- **Admin** (`8610140`): the run-sheet generator's "smart sync" used to delete
  and regenerate every "clean" pending order for the date, which would have
  silently wiped customer edits. It now keeps orders with
  `is_customer_modified = true`.

**Follow-up build error, fixed in `2eaab3f`:** `bulk_modify_subscription.dart`
was a second caller still passing `totalValue`, which broke the release build.
Removed the argument and the now-dead `totalCost` accumulator.

**Status:** ✅ RLS error gone (user confirmed saving works).
⏳ Bulk-modify (multi-day edit) not explicitly re-tested after the fix.

## 3. Day-order save rejected as "unavailable / out of stock"

**Reported:** adding an item (honey) to an existing day's order showed
`One or more items are unavailable, inactive, or out of stock (P0001)`.
A database check confirmed every item involved was active and in stock.

**Root cause:** `subscription_day.dart` rebuilt the subscription line's entry on
every render with `'productId': product.id` — the **product** id, not the
variant id. That value is sent to `modify_daily_order` as the line's
`variant_id`; `internal.normalize_cart` couldn't find it in `product_variants`
and rejected the whole save. The bug predates this week; it was hidden because
saves used to fail earlier on the RLS error (section 2).

**Fix** (`3eafd84`): new `_subscriptionVariantId()` takes the real variant id
from the subscription line, falling back to the product's variant with the same
label/price. `bulk_modify_subscription.dart` already uses variant ids, so it is
not affected.

**Status:** ✅ `flutter analyze` clean.
⏳ **Needs an app rebuild and an on-device test** — add an item to an existing
day and save.

## 4. Notifications admin page: pick recipients by name, see all devices

**Repo:** `Hetha_admin` (`a6e9114`).

**Before:** "Specific User" was a raw `User ID (UUID)` text box — unusable.

**Now:**
- **Send Notification tab:** multi-select customer picker. Type a name, phone or
  email → live results → click to add as a removable chip → send to all
  selected. "All Users" broadcast is unchanged.
- **All Devices tab:** every registered device with customer name, phone,
  email, platform and registered date, plus search and "Load more". Clicking a
  row adds that customer as a recipient and switches to the send form.
- New endpoints, both gated on `notifications:send`:
  `/api/admin/notifications/recipients` (minimal customer search) and
  `/api/admin/notifications/devices` (devices joined to customers — done as two
  queries because `device_tokens.user_id` references `auth.users`, not
  `public.users`).
- The old `send-single` action was folded into the array-based `send-custom`.

**Bug found and fixed along the way — RLS undercounting:** the page showed
"Total Devices: 1" while the database had 5. The routes used the admin's own
session client, and `device_tokens` RLS is "own rows only", so every read
returned just the logged-in admin's own device. That also means the **"All
Users" broadcast had likely been reaching only that admin's device** all along.
Fixed by reading `device_tokens` / `users` with the service-role client in all
three notification routes (access still gated by `requireAdmin`).

**Status:** ✅ user confirmed the page shows real devices and names.

## 5. Cross-account push notification leak (security / privacy)

**Reported:** after logging out of `sudheerchatla5@gmail.com` and into
`gnananidhi1@gmail.com` on the same phone, notifications meant for the first
account still arrived.

**Root cause (two bugs):**
1. Logout never released the phone's FCM token — `profile_page.dart` called
   `auth.signOut()` directly, bypassing `unregisterToken()`.
2. Login never re-registered the token — `registerToken()` only ran once at
   app start.

FCM delivers by token, not by "who is logged in", so the old account's row kept
receiving that account's pushes. A client-only fix was impossible:
`device_tokens` RLS is "own rows only", so the new account cannot delete the
old account's row.

**Fix:**
- **Migration 023** (`docs/db/migrations/023_register_device_token_rpc.sql`,
  applied ✅): `public.register_device_token(token, platform)`,
  `SECURITY DEFINER`. Releases the token from any other account, then claims it
  for the caller. It self-heals on the next login even after a crash or app
  kill.
- **App** (`2eaab3f`): token registration goes through the RPC;
  `unregisterToken()` runs before sign-out; `registerToken()` runs after every
  successful sign-in.
- Docs corrected — `DATA_MODEL.md` previously claimed "token deleted on
  sign-out", which wasn't true. The missing `device_tokens` policy was added to
  `docs/db/policies.sql`.
- The `device_tokens` table was wiped manually for a fresh start. Devices
  re-register the next time each user opens the app.

**How it works now:** one FCM token per app install. The token always belongs
to whichever account is logged in on that install. One account can have several
devices (one row each).

**Status:** ✅ user tested account switching on the same phone.

## 7. Free delivery for serviceable pincodes

**Client rule:** pincodes saved in Delivery Areas / Pincodes are delivered by
Hetha's own riders (no courier), so they pay **no delivery fee**.

**Before:** the fee ignored the address entirely — weight tiers everywhere.

**New rule (server-authoritative):**
- ₹0 when the delivery pincode is in `pincodes` **and** its delivery area is
  active — the same check (`internal.serviceable_area_id`) that controls
  product visibility and the local-only product block.
- Otherwise the weight tiers from `delivery_charge_tiers`; `free_delivery`
  variants still add no weight.
- An area switched off in the admin panel pays tiers again (agreed).

**Changes:**
- **Migration 024**
  (`docs/db/migrations/024_free_delivery_serviceable_pincodes.sql`, applied ✅):
  - New `internal.compute_delivery_charge(items, pincode)`.
  - `public.quote_cart(items, address_id = NULL)` replaces `quote_cart(items)`;
    the address must belong to the caller. Called without an address it gives
    the weight-tier fee, so older app builds keep working.
  - `place_order_core` charges by the order's address pincode (wallet, COD,
    admin, Razorpay).
  - `create_payment_intent` quotes the Razorpay amount with the order's address.
  - The admin fee override is unchanged.
- **App** (`958fe42`): the cart quotes for the **selected (browsing) address**
  (the one that decides which products are shown); checkout quotes for the
  checkout address. The offline fallback follows the same rule.
- **Admin** (`51c92db`): the Create Ad-Hoc Order modal shows ₹0 with
  "(free — <area> pincode)". This change was required because the modal sends
  its fee as an admin override.

**Live data after migration:** 306 free-delivery pincodes — Delhi 55,
Ghaziabad 26, Noida 225, all areas active.

**Status:** ✅ database verified (single `quote_cart(jsonb,uuid)`; anon blocked).
✅ user tested in the app: a Delhi pincode shows ₹0, another address shows the
tier fee.
⏳ Admin ad-hoc order screen not yet tested.

**Admin bypass (explained on request):** when an admin (`orders:edit` / super
admin / service role) places an order, `place_order` uses the fee they send
(minimum ₹0). Customer and Razorpay orders always use the server-computed fee.
Admin orders also skip the 3-day wallet reserve and the local-only product
check. Keep `orders:edit` for trusted staff.
