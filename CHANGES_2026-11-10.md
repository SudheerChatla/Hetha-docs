## 1. Notification tap opens the right tab

Two causes for test 5's "the delivered notification opens Home":

1. **Wrong route.** The admin sent every "delivered" push with
   `route: 'subscription'`, one-time orders included. The app maps that route
   to Home, which holds the subscription calendar.
2. **Taps that launch a closed app were dropped.** `NotificationService.initialize()`
   reads the launching notification (`getInitialMessage`) in `main()`, before
   `runApp`. At that point there is no navigator, so the tap did nothing and
   the app opened on Home.

Fixes:

- **Admin:**
  - `notifyOrderDelivered` is renamed `notifySubscriptionDelivered`; it is
    still `route: 'subscription'` and used for Daily Ops subscription
    deliveries.
  - One-time orders use the new `notifyOrderStatus` with `route: 'orders'`.
- **App:**
  - `NotificationService` no longer switches tabs itself. It closes any pages
    on top of the tabs and leaves the requested tab in `pendingTab`.
  - `MainWrapper` applies it as soon as it is on screen: immediately if the
    app is running, and after start-up or sign-in if the app was closed.

## 2. Pushes for every order status change

Before, `PATCH /api/admin/orders/[id]` only pushed on `delivered`, and the
Deliveries page's "record delivery" sent nothing at all.

| Order status (one-time orders) | Push |
|---|---|
| `processing` | "Order Confirmed ✅" |
| `shipped` | "Order Shipped 📦" |
| `out_for_delivery` | "Out for Delivery 🚚" |
| `delivered` | "Order Delivered! 🥛", plus the refund for a short delivery |
| `cancelled` | "Order Cancelled", plus the refund when nothing could be delivered |
| `payment_pending`, `placed` | none: the customer just did this in the app |

- Every body names the order number. All pushes open the **Orders** tab.
- **Only on a real change.** The route reads the old status first, so saving
  the same status again (for example to edit tracking only) doesn't push twice.
- **Deliveries page:**
  - `record-order-delivery` pushes delivered or cancelled with any wallet refund.
  - `record-subscription-delivery` pushes "delivered" once the daily order is
    delivered (Daily Ops already did this).

## 3. Pushes are no longer cut off on Vercel

Pushes were started "fire-and-forget" after the response was sent. On Vercel
the function can end as soon as the response is out, killing an unfinished
push. All pushes in the Daily Ops, Orders and Deliveries routes now run inside
Next.js `after()`, which keeps the function alive until they finish. This
covers delivered, wallet debited, low balance and order status pushes.

## 4. Live updates recover right after a network change

Test 6: Orders screen open, Wi-Fi off, order changed in admin, Wi-Fi on → no
update until pull-to-refresh.

**Cause:**
- After the network goes away, the Realtime WebSocket is dead, but
  realtime_client 2.7.3 keeps reporting it as connected until a heartbeat goes
  unanswered (25 s interval; 25–55 s to notice).
- Until then nothing reconnects. supabase_flutter's own recovery also skips a
  socket it believes is connected (`supabase.dart:268`).
- `LiveChannel` (2026-11-08) did refetch once the library finally rejoined,
  but that was up to a minute later.

**Fix:** new `lib/services/realtime_network_watcher.dart`, started in `main()`.

- It watches the phone's network with `connectivity_plus`.
- When the phone comes back online or switches network (Wi-Fi ↔ mobile data),
  it does what supabase_flutter does on resume:
  1. fresh socket (`disconnect()` + `connect()`);
  2. `forceRejoin()` for every joined channel.
- The rejoin makes each `LiveChannel` report `subscribed` again, so the Orders
  and Wallet screens refetch what changed while offline.
- **When it does nothing:**
  - in the background (supabase_flutter handles resume);
  - when there are no channels;
  - when going offline (no network to reconnect on yet).
- Reconnects are serialised.
- Decision logic is in `lib/utils/network_change.dart`, with tests in
  `test/network_change_test.dart`.

## 8. Orders page: status change shows instantly

Requested by Sudheer: after picking a status and clicking ✓, the page gave
no sign anything was happening.

**Measured on the local panel, before the change:**
- Clicking ✓ showed nothing for 3.3 s (6.3 s the first time): no spinner,
  and the editor stayed open with ✓ still clickable.
- Then "Status updated" appeared, but the row **still showed the old
  status**.
- The new status only appeared after the whole list was downloaded again:
  4.7 s after the click (13 s the first time).

**Changes:**

- **Optimistic update** (`app/admin/orders/page.tsx`):
  - On ✓ the row shows the new status at once with a small spinner, and its
    edit button is disabled until the save finishes.
  - A failed save puts the old status back with an error message.
  - Saving the same status does nothing.
- **No list reload:**
  - The row is updated from the save's reply; other cached pages are only
    marked stale, so a filtered view reloads when next shown.
  - An in-flight list refetch is cancelled so it can't overwrite the new
    status.
- **One-query save** (`app/api/admin/orders/[id]/route.ts`):
  - `update … where status <> new status returning …` replaces "read old
    status, then update", saving one round trip.
  - A returned row means the status really changed, so a push still goes out
    only on a real change.
  - Only when nothing changed does a second query tell "same status" (200)
    from "no such order" (404).
  - The reply now includes the saved status.

**Checked on the local panel** (Shipped → Out for Delivery → Delivered):
- The new status appeared **26–61 ms** after ✓, and the server save then
  took 1.9 s locally.
- A same-status save sent no request.
- A page reload showed the saved status.
- `tsc`, lint and `npm run build` pass.

The remaining server time (several login/permission lookups per request) is
the admin-wide speed item from the 2026-11-09 review, not this page.

## 9. Smooth sidebar and page switching

Requested by Sudheer: the green sidebar highlight and the page content
switched abruptly.

**Sidebar (`components/admin/AdminSidebar.tsx`):**
- **Sliding highlight.** One green pill behind the menu glides to the active
  item over 200 ms (ease-out), instead of each item switching its own
  background on and off.
  - The pill measures the active link and sets its own `transform`/`height`
    in a layout effect: no React state, so no extra render.
  - The first placement on page load doesn't animate; a `ResizeObserver`
    keeps it aligned when items shift (permissions, resize).
- **Active on click.** The clicked item becomes active immediately, instead
  of when the new page has loaded. `useLinkStatus` was not used: the docs say
  it skips the pending state for prefetched links, which is most of the menu.
  - Ctrl/Cmd/Shift/middle-clicks, which open a new tab, are ignored.
  - The text colour and chevron fade instead of switching.
- `aria-current="page"` is now on the active link.

**Page content (`app/admin/template.tsx`, `app/globals.css`):**
- Every page fades in and rises 6 px over 180 ms. The template is re-created
  on each navigation, unlike the layout, so this plays on every switch.
- The animation uses `backwards` fill, so no `transform` stays on the wrapper
  afterwards. A leftover transform would make `position: fixed` modals
  position against the wrapper instead of the window.

All of it is off for users with "reduce motion" set in their OS
(`motion-reduce:` / `prefers-reduced-motion`). The experimental View
Transitions flag was not used (Next.js advises against it in production), and
no animation library was added.

**Checked** on a local production build (`next start -p 3001`), Orders →
Customers:
- URL changed at 37 ms, and the highlight was on Customers from the first
  frame.
- The pill went 159 → 193 → 198 px in about 150 ms.
- Page opacity went 0 → 0.89 → 1.0 in about 170 ms; final transform `none`.
- The "Add customer" modal opens centred.
- On the dev server, the highlight moved at 21 ms while the page was still
  compiling.
- `tsc`, lint and `npm run build` pass.

The dev server that was already running did not pick up the `globals.css`
change; the production build output contains the rules. Restart
`npm run dev` to see the fade there.
