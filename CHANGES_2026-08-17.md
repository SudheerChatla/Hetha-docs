# Changes — 2026-08-17

Scope: Customer app (`Hetha_app`) only. No database schema changes, no admin
panel changes. Covers a removed feature, a cart data-integrity fix, an
address-selection UI change, and a UI flicker fix — plus the decisions/
alternatives discussed and explicitly rejected along the way.

---

## Removal: "Buy Now" (direct-buy) checkout path

### What changed

- Removed the **Buy Now** button from the product details page. Only the
  quantity selector and cart button remain in the bottom action bar.
- All purchases now go through **Add to Cart → Cart → Checkout**. There is no
  longer a way to skip the cart.

### Why

- The business model is a daily-subscription grocery/dairy service, not an
  impulse-buy marketplace — basket-building via the cart is the primary path,
  and Buy Now was a secondary, rarely-differentiated flow.
- Buy Now bypassing the cart had already caused a real bug (documented in the
  pre-existing code comments): the delivery-charge calculation showed ₹0.00
  for a direct buy because it was keyed off the cart, not the route arguments.
  Removing the second path removes the class of bug entirely instead of
  patching around it.
- Two parallel checkout paths (cart-based and direct-buy) meant every future
  change to pricing, delivery-charge tiers, or the 3-day wallet buffer rule
  had to be verified against both paths. Money-related logic is exactly where
  you want a single path, not two.

### Files changed

- `Hetha_app/lib/screens/product/product_details_page.dart` — removed the
  Buy Now button and its route-argument-passing logic; simplified
  `_floatingBottomBar` (dropped the now-unused `variant` parameter it only
  needed for Buy Now).
- `Hetha_app/lib/screens/checkout/checkout.dart` — removed all
  `isDirectBuy`/`directItems` branching (route-argument reading, conditional
  cart-clearing, conditional loading/error states). Checkout now
  unconditionally reads from `cartState.items`. Removed `_pendingIsDirectBuy`
  field and the `isDirectBuy` parameter from `_startRazorpayPayment` /
  `_handleRazorpaySuccess`.
- `Hetha_app/lib/providers/delivery_charges_provider.dart` — updated stale
  doc comments that referenced the Buy Now bypass rationale. The
  signature-based delivery-charge provider itself was kept (still useful for
  quoting a charge on an explicit line-item set), only the comments changed.

### Verified

- Grepped the entire `Hetha_app` tree for `isDirectBuy`, `directItems`,
  `Buy Now`, `buy_now`, `buyNow` — zero matches remain.
- `flutter analyze --no-fatal-infos` — **No issues found!** (no compile
  errors, no unused-parameter warnings from the removal).
- Confirmed only one call site navigates to `/checkout`
  (`cart_page.dart:161`) and it passes no route arguments, so the whole
  `arguments`-map pattern on that route is fully retired, not just unused in
  one spot.

## Fix: Cart items disappearing / cart failing to load on first launch

### Symptoms reported

1. Adding a second product to the cart, then pulling to refresh, sometimes
   made the second product disappear (the first one survived).
2. On first-ever use, the cart badge/page sometimes failed to load at all,
   but the item turned out to have been added successfully once the app was
   closed and reopened.

### Root cause

**Cart writes to Supabase were optimistic-UI-first, fire-and-forget, and
unserialized.** `CartNotifier.addToCart` (and `removeFromCart`,
`updateItemQuantity`) updated the local in-memory state instantly (correct,
intentional — that's what makes the UI feel instant), then kicked off an
`await updateCart()` call to Supabase *without* the caller awaiting it and
*without* any queuing between overlapping calls.

`CartService.updateCart`'s delete step deleted **"everything not in the
snapshot passed to this particular call"** — which was fine for a single
call, but not safe under concurrency. If two `addToCart` calls fired close
together (e.g. tapping product A, then quickly tapping product B before A's
network write finished), their two Supabase writes could resolve in either
order. If the write for A (which only knew about A) resolved *after* the
write for B (which knew about both), A's delete step would delete B from the
server — even though B was added correctly and shown correctly in the UI the
whole time. Pulling to refresh then re-fetched from Supabase and exposed the
loss.

Separately, `fetchCart()` silently swallowed any fetch error into an empty,
non-error `CartState` — indistinguishable from a genuinely empty cart. A
transient failure on a cold-start fetch (e.g. auth/session not fully warm
yet) looked exactly like "the cart is empty," which is what produced the
"cart never loaded" symptom until app restart gave the fetch a second,
successful attempt.

### Fix

- `Hetha_app/lib/providers/cart_provider.dart`:
  - Added a `_writeQueue` (chained `Future`) inside `CartNotifier`. Every
    Supabase write now goes through a new `_enqueueWrite()` helper, which
    chains onto the previous write so writes are applied strictly in the
    order they were issued, regardless of individual network latency —
    eliminating the out-of-order-write race.
  - `addToCart`, `removeFromCart`, `updateItemQuantity`, and `clearCart` now
    pass an explicit `removedKeys` set for whatever they are actually
    removing, instead of relying on a full-snapshot diff.
  - `fetchCart()` now sets `errorMessage` on the `CartState` when the fetch
    throws, instead of resetting to a plain empty state.
- `Hetha_app/lib/services/cart_service.dart`:
  - `CartService.updateCart` signature changed to
    `updateCart(Map<String, int> quantities, {Set<String> removedKeys = const {}})`.
    It now deletes **only** the explicit `removedKeys` (via `.inFilter`),
    replacing the old "delete everything not in this snapshot" logic that was
    unsafe under concurrent/out-of-order calls.

### Why this fix and not something else

- Considered but rejected: just awaiting `addToCart` at every call site.
  This alone wouldn't have fixed it — the race was between two *separate*
  async operations each already being awaited correctly within their own
  call; the problem was the lack of ordering *between* those two operations,
  not a missing `await` on any single one.
- The explicit-`removedKeys` approach was chosen over "delete everything not
  in the latest snapshot" specifically because the latter's correctness
  depends on every write happening in issue-order — which is exactly the
  invariant the write queue now guarantees, but relying on both mechanisms
  independently would have been fragile. Making deletes explicit means even
  if ordering were ever violated by a future change, a stale write can no
  longer delete an item it was never told to remove.

### Verified

- `flutter analyze --no-fatal-infos` — **No issues found!**
- Confirmed `.inFilter(...)` is an established call pattern already used in
  four other files in this codebase (`subscription_service.dart`,
  `checkout.dart`, `walletpage.dart`, `delivery_charge_service.dart`), so the
  new delete call follows existing conventions rather than introducing a new
  one.
- Confirmed via grep that no other file calls the now-removed public
  `CartNotifier.updateCart()` method — it was only ever called internally,
  so refactoring it into the private `_enqueueWrite` broke no other call
  site.
- Confirmed `cart_page.dart` already listens to
  `cartNotifierProvider.select((s) => s.errorMessage)` and shows a red
  `SnackBar` on it — this UI wiring already existed but was never actually
  triggered before this fix, since `fetchCart()` never populated the field.

### Not yet independently verified (documented, not assumed fixed)

- Have not run the app on a device/emulator to reproduce the original
  two-quick-adds-then-refresh scenario end-to-end against a live Supabase
  instance.
- Have not reproduced the cold-start "cart doesn't load" scenario against
  real auth/session timing — that diagnosis was inferential from reading the
  code (the silent-catch pattern), not observed directly in a running app.

## Address selection UI: added a "Selected" badge, removed redundant selection UI

### Discussion and decisions made (in order)

1. **Initial ask**: remove "Buy Now" — covered above, unrelated to addresses,
   listed here only for chronology.
2. **Cart race condition** — covered above.
3. **Reference screenshot review**: user shared a Swiggy/Blinkit-style
   "Select Your Location" screen (search bar, Use Current Location, Add New
   Address, Request Address, saved addresses with a `SELECTED` chip and
   per-address distance). Discussed merits; **no changes made** at that
   point — explicitly deferred (search bar, current-location detection,
   distance labels, "Request Address" equivalent, and per-item overflow menu
   were all identified as candidates but **not implemented** this session).
4. **User's actual ask**: remove the existing "Default"/"set as default"
   concept from the address list, replacing it with only a "Selected" badge
   (matching the screenshot), where the selected address should also drive
   product listings and default the checkout address — while keeping the
   option to change it inside checkout.
5. **Key open question resolved**: should changing the address *inside
   checkout* be (A) one-time/checkout-scoped, or (B) persist back to become
   the new globally-selected address? **Decision: (A), one-time.** This
   matches the app's pre-existing, deliberate design — `SelectAddressPage`
   already has a `fromCheckout` flag whose explicit purpose (per its own
   code comments) is to keep checkout-time address changes local-only and
   never persist them as the new default. No code change was needed for
   this — it was already correct; the decision was to **not** change it.
6. **DB question raised**: does removing "Default" require a database
   change? **Decision: no.** Investigation found `is_default` is load-bearing
   for the **admin panel** — `CreateOrderModal.tsx` and `CreateSubModal.tsx`
   in `Hetha_admin` use `addresses.find(a => a.is_default) || addresses[0]`
   to prefill the ship-to address when staff manually create an order or
   subscription. It's also asserted directly in the money-integrity test
   suite (`docs/db/tests/verify_money_integrity.mjs`). **`is_default` was
   left completely untouched in the database, in `AddressService`, and in
   the admin panel.**
7. **Follow-up question**: could `is_default` be renamed/repurposed to mean
   "selected" in the DB instead of using `SharedPreferences`? **Discussed and
   explicitly rejected for now.** Reasoning: it would turn every address
   selection into a network round-trip with the same class of race condition
   just fixed in the cart; it would change the admin panel's prefill
   semantics from "stable default" to "whatever the customer last happened
   to be browsing"; and it solves a cross-device-sync problem nobody asked
   for. `SharedPreferences` (already implemented via
   `browsingAddressIdProvider` / `browsingAddressProvider`) was confirmed
   sufficient for the stated requirement.
8. **Final, narrowed ask**: don't change any underlying behavior at all —
   purely add a visible "Selected" badge (styled like the screenshot's green
   chip) showing which address is actually driving the home page right now,
   sourced from `browsingAddressProvider`. Keep the "Default" badge exactly
   as-is. In discussing this, established that the pre-existing border/
   elevation on the card and the "Selected for Delivery" checkmark row were
   **redundant with the "Default" badge** (both were driven by the same
   underlying `is_default`-sourced value in the normal, non-checkout flow),
   so removing that redundant markup and replacing it with two clean,
   independent badges was agreed as the better version of the same idea.

### What actually changed

- `Hetha_app/lib/screens/address/select_address_page.dart`:
  - Added `browsingAddressProvider(userId)` as a new watch in `build()`.
  - `_buildAddressCard` now takes a `browsingAddressId` parameter and shows a
    new green **"Selected"** badge next to the address name when
    `browsingAddressId == address.id` — independent of, and can appear
    alongside or separately from, the existing "Default" badge.
  - Removed the `isSelected`-driven `Card` border color/width and elevation
    (previously brown-outlined + elevated when `_locallySelectedAddress`
    matched — which in the normal open-from-home-page flow was always just
    re-showing the DB default).
  - Removed the "Selected for Delivery" checkmark row underneath the address
    text, for the same reason — redundant with "Default" in this flow.
  - **Not changed**: `_locallySelectedAddress` and every one of its other
    uses — constructor initialization from `widget.currentAddress`, the tap
    handler assignment, the persisted-value backfill via
    `persistedSelectedAddressAsyncValue`, `PopScope`'s pop-with-result logic,
    and the "Deliver to This Address" button. All of that state and
    behavior is untouched; only the two pieces of *visual markup* that read
    it were removed.
  - **Not changed**: `is_default` in the database, `AddressService`,
    `activeAddressActionProvider`, `setAddressAsDefault`, or anything in
    `Hetha_admin`.

### Verified

- Grepped every usage of `_locallySelectedAddress` in the file after the
  change (5 matches outside the card builder) to confirm the pop/persist/
  button logic still reads the exact same variable, untouched.
- `flutter analyze --no-fatal-infos` — **No issues found!** (confirms no
  unused variables or broken references from removing the border/checkmark
  markup).

## Fix: Home page location chip flashing the previous address on navigation

### Symptom reported

With two saved addresses (e.g. "Ghaziabad" and "Noida"), after selecting
Ghaziabad and then navigating to another page (e.g. the products page) and
back to the home page, the location chip would briefly flash "Noida" before
immediately correcting itself back to "Ghaziabad".

### Root cause

`_buildLocationInfo()` in `home_page.dart` computed the displayed location as
`browsingAddress?.city ?? userData?.area ?? ''` **inside** the `data:`
branch of `userDataAsync.when(...)`, and cached the result into
`_lastKnownLocation` / `_lastKnownPincode` fields used only as the fallback
for the `loading:` and `error:` branches.

`browsingAddress` itself (from `browsingAddressProvider`, backed by
`SharedPreferences` via `browsingAddressIdProvider`) is **synchronous** and
never in a loading state — selecting a new address updates it instantly.
But because the *combined* location string was only recomputed while
`userDataAsync` was in its `data` state, any transient reconnect/rebuild of
`userDataAsync` (a `StreamProvider` following a live Supabase stream,
plausible on navigating away from and back to the home page) caused the
widget to briefly fall into the `loading:` branch and redisplay whatever
`_lastKnownLocation` had cached from **before** the most recent address
switch — the visible flash — until `userDataAsync` resolved back to `data:`
and corrected it.

### Investigation into `userData.area` / `userData.pincode`

Before fixing, confirmed what these legacy fields actually represent, since
the fallback path depends on them:

- They are plain columns on the `users` table (`area text`, `pincode text`),
  entirely separate from the `addresses` table — **not** derived from or
  linked to any address, default or otherwise.
- Grepped the entire customer app for any write to `users.area` or
  `users.pincode` — none exists. `edit_profile_page.dart`'s `_updateProfile`
  only writes `first_name`/`last_name`.
- Found an explicit comment in `user_area_service.dart` stating this field
  is legacy: *"Service to retrieve user's delivery area information from
  their active subscription — this replaces the redundant area field that
  was previously stored in user documents."*
- Conclusion: for most users this field is `null` or a stale historical
  value with no ongoing maintenance. It was left in place as a last-resort
  fallback (harmless — if both `browsingAddress` and `userData.area` are
  unavailable, the chip shows "Select location" either way) but was **not**
  fixed, repopulated, or removed — that would be a separate, unrelated
  decision if revisited later.

### Fix

`Hetha_app/lib/screens/home/home_page.dart` — `_buildLocationInfo()`
restructured to check `browsingAddress` **first** and return immediately
when it's non-null, entirely bypassing `userDataAsync` (and therefore its
loading-state flicker) for that render:

```dart
if (browsingAddress != null) {
  final location = browsingAddress.city.isNotEmpty ? browsingAddress.city : 'Select location';
  final pincode = browsingAddress.pincode;
  _lastKnownLocation = location;
  _lastKnownPincode = pincode;
  return _buildLocationDisplay(location, pincode);
}
// only reached when there is no browsing address at all:
final userDataAsync = ref.watch(userDataProvider);
return userDataAsync.when(...);
```

`userDataProvider` is now only watched/read at all when there's no browsing
address selected — the common case (a returning user with a selected
address) never touches the stale-cache fallback path anymore.

### Verified

- Confirmed `Address.city` and `Address.pincode` are non-nullable `String`
  fields (not `String?`), so `.isNotEmpty` is safe without an additional
  null check.
- `flutter analyze --no-fatal-infos` — **No issues found!**

### Also clarified in discussion (no code change)

User asked whether the app forces an address-selection prompt on every
launch. Checked `main.dart` (routes straight to `AuthWrapper` → home page,
no forced address screen) and `home_page.dart`'s `initState` (only calls
`_initializeData()`, no navigation to any address picker). Confirmed: the
app does **not** auto-prompt for address selection on open; the location
chip silently resolves the previously-stored `browsingAddressId` and only
navigates to the address picker if the user taps the chip themselves.
