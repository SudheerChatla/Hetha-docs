## 1. Background: the 2026-10-15 investigation

Reported problem: live updates on the Orders and Wallet screens "sometimes
work, sometimes not".

- **Database side checked and correct:** `users`, `orders`, `order_tracking`
  and `subscription_daily_orders` are in the `supabase_realtime` publication
  with all columns (`order_tracking` includes `user_id`); no leaked
  subscriptions; DB connections 21 of 60.
- **Two-phone test + Supabase API logs (2026-10-14 19:54–20:06 UTC):** on one
  phone the screen re-fetched about 1.3 s after each admin change. On the
  other, **nothing** fired for 6 order changes and 2 wallet top-ups, although
  its socket was connected and the app was in the foreground.
- **Root cause for that phone:** it signed in through *Forgot password*
  (`/auth/v1/recover` → `/auth/v1/verify`). gotrue reports that as
  `passwordRecovery`, and supabase_dart only passes the user's token to
  Realtime on `initialSession`, `signedIn` and `tokenRefreshed`
  (`supabase_client.dart:373`). Realtime stayed on the anon key, so RLS hid
  every change, until a token refresh (~1 h) or an app restart.
- **Other defects found in the code and client library** (realtime_client
  2.7.3, supabase_flutter 2.12.4):
  1. A notification tap pushed a second `OrderPage` with the same channel
     topic; realtime_client's `leaveOpenTopic` unsubscribed the Orders tab's
     channel, which stayed dead.
  2. The 20-second resume rule assumed the socket survives short trips to the
     background; supabase_flutter closes it on `paused`, so changes made
     during a quick app switch were lost.
  3. A rejected join (e.g. expired token on resume) is never retried, and
     supabase_flutter's resume only rejoins channels that were joined.
  4. supabase's `.stream()` closes for good if its refetch after a reconnect
     fails; `userDataProvider` then shows a frozen balance for the session.
  5. The Orders screen didn't refetch after a reconnect while open, and
     ignored errors and closes.

Monitoring queries written that day (SQL Editor):
`realtime.subscription` per table / per user / duplicates,
`pg_publication_tables`, `pg_replication_slots` lag, `pg_stat_activity`.

## 2. `LiveChannel`: a Realtime channel that recovers on its own

New `Hetha_app/lib/services/live_channel.dart` (+ `lib/utils/live_channel_backoff.dart`).
Both Realtime users in the app now go through it.

| Behaviour | Fixes |
|---|---|
| Calls `onResync` every time the channel is joined **again** (resume, reconnect, rebuild) so the owner refetches | missed events (§1 items 2, 5) |
| On error / timeout / unexpected close: after 3 s → 6 s → 15 s → 30 s, if still not joined, removes the channel and builds a new one | rejected joins (item 3), dead channels |
| No rebuilds while the app is in the background (would reopen the socket); rebuilds on resume if not joined | battery, background sockets |
| Before every (re)build, refreshes an expired session and calls `realtime.setAuth` with the user's token | expired-token joins, wrong identity |
| Unique topic per build (`<name>-<n>`) | topic collision (item 1) |
| New channel is created **before** the old one is removed | avoids the socket closing when the last channel is removed, racing the new connect |

## 3. "Forgot password" logins get live updates

`LiveChannel` listens for `passwordRecovery`. When it brings a token the
channel wasn't built with, the channel is rebuilt with that token. New
channels always sync the token first (§2), so screens opened after a
recovery login join as the user, not as anon.

## 4. Wallet stream can no longer die

`UserService.streamUserData` no longer uses supabase's `.stream()`. It
fetches the row, applies changes from a `LiveChannel` (same as before:
`newRecord` on insert/update, null on delete), refetches on every rejoin, and
retries a failed fetch every 5 s instead of closing the stream. Only the
first load reports an error; later failures keep the last good row.
`userDataProvider` and every screen using it are unchanged.

## 5. Orders screen and the 20-second rule

- `order_page.dart` uses `LiveChannel` (same two filtered listeners on
  `orders` and `order_tracking`). Its `onResync` triggers the existing
  debounced refetch. The lifecycle observer and `ResumeRefreshPolicy` are
  gone: the resync on rejoin covers resume exactly.
- Wallet tab: refreshes on every return from `paused`, however short.
  `inactive` alone (notification shade) keeps the socket and does nothing.
- Deleted `lib/utils/resume_refresh_policy.dart` and its test (no users left).

## 6. Notification taps switch tabs

`notification_service.dart` no longer pushes `/orders`, `/wallet` or a
second `/home`. A tap pops back to the tabs and selects Orders (2), Wallet
(3) or Home (0) through `navigationIndexProvider`
(`lib/utils/notification_route.dart`). The `/orders` and `/wallet` routes
remain (Create Subscription still pushes `/wallet`); with unique topics a
pushed copy no longer breaks the tab.

## 7. Device test

Run on 2026-11-08 with the release APK (`app-arm64-v8a-release.apk`) on two
phones and the admin panel on a laptop. The plan sent to the tester had 7
steps; results:

| # | Test | Result |
|---|---|---|
| 1 | Code entry screen (§10) | ✅ |
| 2 | Forgot-password login gets live updates (§3) | ✅ |
| 3 | Normal login: orders + wallet live (§4, §5) | ✅ |
| 4 | Quick app switch (§5) | ✅ |
| 5 | Notification tap opens Orders (§6) | ❌ see below |
| 6 | Network drop: list refreshes after reconnect (§2) | ❌ see below |
| 7 | Quick regression checks | ✅ |

**Test 5 findings (open):**
- Tapping the "order delivered" notification opens the app on **Home**, not
  the Orders tab.
- Order notifications arrive **only for "delivered"**; other status changes
  (confirmed, out for delivery, …) send no push. This is on the
  sending side (DB trigger / Edge Function), not in this change.

**Test 6 findings (open):** Orders screen open on one phone, Wi-Fi turned
off, order changed in admin, Wi-Fi back on after a while → the list did
**not** update by itself; only pull-to-refresh showed the change. So the
channel did not rejoin (or rejoined without `onResync`) after the network
came back while the app stayed in the foreground.

Original checklist:

1. **Normal login:** phone on Orders; change an order in admin → updates in
   1–2 s. Wallet top-up → balance updates in 1–2 s.
2. **Forgot-password login:** sign in through Forgot password (OTP), repeat
   step 1 → updates arrive (before: nothing until restart). Optional check in
   the SQL Editor: `select claims->>'role', claims->>'sub', entity::text from
   realtime.subscription;` shows `authenticated` for that user.
3. **Quick app switch:** switch away, change an order in admin, come back
   within 10 s → the change shows.
4. **Notification tap:** tap an order notification → Orders tab opens; go
   back and change another order → still updates live.
5. **Network switch:** toggle airplane mode for ~30 s, change an order
   meanwhile, turn it off → list refreshes after reconnecting.

This also covers the open device tests from 2026-10-04 (migration 035) and
2026-10-06/08 (wallet live balance).

## 10. Code entry screen: one box per digit

Requested by Sudheer. `verify_email_page.dart` is the only code-entry screen
(used for both *Forgot password* and new-account email verification; the
admin panel has none), so both flows get it.

| Before | After |
|---|---|
| One wide box | Six small square boxes, one per digit, centred and sized to fit narrow phones (max 52 px) |
| `• • • • • •` placeholder shown before typing, which looked like a code was already entered | Boxes are empty until a digit is typed |
| — | The box taking the next digit has a dark border and a blinking cursor; filled boxes get a brown border |
| Error shown only in the banner | Boxes also turn red while the error is showing; the code is cleared as before |

Behaviour kept: digits only, auto-submit on the 6th digit, Verify button,
resend cooldown. New `lib/widgets/otp_code_input.dart` draws the boxes over
a single invisible `TextField`, so email/SMS code autofill, paste,
Backspace across boxes and screen readers ("Verification code, 6 digits")
work as before.

⏳ Device check: open Forgot password, confirm empty boxes, type, Backspace,
paste a code from the email, enter a wrong code (red boxes), then a right one.
