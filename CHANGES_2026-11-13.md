## 1. Migration 037: one settlement function

`docs/db/migrations/037_daily_order_settlement.sql`

**Problem.** Finalize debited each daily order once and kept only a flag
(`payment_status = 'paid'`). Nothing recorded how much was taken, so nothing
could correct it later: a failed debit still went out unpaid, short deliveries
were never refunded, a skip or cancel after finalize refunded nothing, and
edits after an unlock were never charged or refunded.

**The idea.** Each order records `paid_amount`, the net amount taken from the
wallet for it. `internal.settle_daily_order` compares that with what the
customer owes now and moves only the difference.

| Order state | Owed |
|---|---|
| Skipped or cancelled | ₹0 |
| Item with a recorded delivered quantity | price × delivered quantity |
| Item without one | price × ordered quantity |

**Actions, each one all-or-nothing database function:**

| Function | Behaviour |
|---|---|
| `finalize_daily_run` | Charges each wallet order. Wallet short → the order is **skipped** (`skip_reason = 'insufficient_balance'`), nothing is taken, and it is reported. Also refunds any skipped/cancelled order of the day that still holds money. Same signature as before. |
| `record_subscription_delivery` | Stores a delivered quantity for every item, marks delivered (cancelled if nothing was delivered), refunds the shortfall. Repeating it moves nothing; a correction settles the difference. |
| `set_daily_order_status` | Skipped/cancelled refunds; back to pending clears quantities and charges again; delivered records full quantities. |
| `retry_daily_order_payment` | Charges a payment-skipped order and puts it back, once the customer has recharged. |
| `unlock_daily_run` | Reopens pending orders. Paid amounts stay, so the next finalize settles only the difference. |
| `reconcile_daily_run` | Refused while any pending order has an item with no delivered quantity; nothing is assumed delivered. Once every quantity is entered: marks the rest delivered, settles every order, closes the day. |

**The four points Sudheer asked for:**

1. **Backfill from verified wallet history.** `paid_amount` for existing
   orders is the net of the order's own wallet transactions
   (`reference_type = 'subscription'`, `reference_id` = order id), not the
   order total. Where the ledger and `payment_status` disagree, the order is
   not guessed at: `settlement_hold_reason` is filled in and no function moves
   money for it until it is reviewed. Held cases: marked paid with no
   transaction; paid with a ledger amount different from the total; marked
   pending/failed/refunded with money still charged; more refunded than
   charged; and orders that went out under the old system with a failed debit.
2. **Deterministic charging priority.** Per customer, oldest subscription
   first (`subscriptions.created_at`, then subscription id). If the wallet
   cannot cover every order, the older subscription is delivered and the
   newer one is skipped.
3. **Reconcile settles only from recorded quantities.** Per Sudheer's
   decision (below), reconcile is refused while any pending order has an item
   with no delivered quantity. It never fills one in.
4. **Skipped orders excluded.** See §2.

**Two extra guards added during self-review:**
- An order with `paid_amount > 0` cannot be deleted (trigger). Cancel it
  instead, which refunds it.
- Cancelling or skipping a paid order while the day is unlocked refunds it
  immediately; finalize also sweeps up any that were missed.

**Tests added (section 11, 98 tests),** covering the list Sudheer asked for:

| Asked for | Covered by |
|---|---|
| Duplicate finalize | second finalize refused, wallet and ledger unchanged |
| Repeated delivery recording | same quantities again moves nothing; correction up charges the difference; correction the wallet cannot cover is refused and changes nothing |
| Unlock, edit, finalize again | add item → +₹100 only; remove item → ₹100 refund; no edit → nothing; enlarged beyond the wallet → skipped and the earlier ₹200 returned |
| Partial deliveries | 1 of 2 short → ₹100 refund; nothing delivered → cancelled and full refund |
| Refunds | staff skip/cancel after finalize; undo; cancel on an unlocked day; finalize refund sweep |
| Insufficient balance | older subscription charged, newer skipped; run totals leave it out; another customer unaffected |
| Payment retries | refused while still short; succeeds after recharge; second retry refused; refused on a reconciled day |

Also: the backfill cases above, permission checks on every function, an order
on hold never being settled, cash-on-delivery orders never touching the
wallet, a reconciled day refusing every money action, the ledger equalling
`paid_amount` for every settled order, no wallet going negative, grants, and
re-running the migration.

## 2. Admin panel

| Area | Change |
|---|---|
| Finalize | Notifications now come from what finalize did: "wallet debited" only for a real debit, and a new "delivery skipped, recharge to resume" push for skipped orders. The toast says how many were skipped. |
| Run sheet | A skipped order shows "SKIPPED: LOW BALANCE" with a **Retry payment** button. Its status dropdown is disabled (use Retry). "Total Orders" became "Orders Going Out". |
| Reconciliation tab | Per-row status changes now work on a finalized day (they were blocked by the lock before). Retry payment button. Delivered count is out of orders going out. |
| Reconcile | One database call. Refused, with the number of orders still missing quantities, until every pending item has one. The reconciliation tab shows that number beforehand. The toast reports refunds. |
| Unlock | One database call. |
| Status changes | Bulk and single go through `set_daily_order_status`; the toast reports any refund or charge. `update-order` no longer accepts `is_finalized` from the browser. |
| Deliveries page | Recording a subscription delivery uses `record_subscription_delivery`; the customer gets a refund push when something was short. |
| Remove last item | If the order was already charged, it is cancelled and refunded instead of deleted. |
| Delivered quantity boxes (run sheet) | Now work on a finalized day (blocked only once reconciled), since reconcile needs them. A quantity must be a whole number from 0 to the ordered quantity. A save that fails shows an error and puts the old value back; before, it failed silently. |

**Skipped (and cancelled) orders are left out of:**
- Live Status packing counts (`getLiveStatus`)
- Route sheets (`getOrdersForSheets`)
- CSV export (`getExportData`)
- Deliveries page stops, rider list and totals (`getDeliveries`)
- Run-sheet order count and day value, and the run's stored totals

They stay visible on the Daily Ops run sheet and reconciliation table, with
the reason, so staff can see why a customer is missing.

## 5. Sudheer's decisions (2026-11-13) and things to know before applying

**Decisions:**

| Question | Decision | State |
|---|---|---|
| Blank delivered quantities at reconcile | **Do not allow reconcile** until staff enter the delivered quantity for every pending item | ✅ implemented and tested |
| Cancelled subscription orders | **Hide** them on the Deliveries page; keep them reachable in the Reconciliation tab | ✅ as built |
| Old unpaid deliveries | **Keep on hold**; never collect automatically | ✅ as built |

**How staff record quantities** now that reconcile requires them:
- Deliveries page: record the delivery (settles at once, refunds a shortfall).
- Daily Ops run sheet: expand the order and type the delivered quantity
  (saved; settled at reconcile).
- Or select orders and "Mark Delivered", which records them as delivered in
  full. That is an explicit staff action, not an assumption by reconcile.

**To know before applying:**
- **Rollout order:** apply migration 037 first, then deploy the admin panel.
  The old panel keeps working against the new database; the new panel does
  not work without the migration.
- **Pick a quiet moment.** Best applied when no day is finalized-but-not-
  reconciled. Orders from such a day with a failed debit are put on hold by
  the backfill and are not charged, but they will show as "could not be
  settled" when that day is reconciled.
- **Run verification query 1** after applying. Any order it lists is on hold
  and needs a look; the migration file shows how to release one.
- **Correcting a delivery upward needs wallet balance.** If a short delivery
  was refunded and is then corrected to a higher quantity, the difference is
  charged; if the wallet cannot cover it, the correction is refused.
- **The customer app** shows nothing new. A skipped order has
  `status = 'skipped'` as before; the reason is only in the push notification.
