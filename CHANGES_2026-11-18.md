## 1. Database (migration 043)

Postgres runs in UTC, so `CURRENT_DATE` is still yesterday between 00:00 and 05:30 IST.

| Function | Before | Effect of the bug |
|---|---|---|
| `public.cancel_subscription` | immediate cancel cut-off = `CURRENT_DATE`; end date read in UTC | Admin cancel between 00:00–05:30 IST also deleted **today's** pending delivery |
| `internal.modify_daily_order_core` / `internal.modify_daily_orders_bulk_core` | "date has passed" check on `CURRENT_DATE` | Yesterday's day still counted as editable until 05:30 IST. The cut-off rule and the finalized lock usually refused these edits anyway. |
| `public.set_product_archived` | "item still running" check on `CURRENT_DATE` | An item that ended yesterday still counted as running until 05:30 IST |

The bodies are copied unchanged from 039, 030 and 028, apart from the date lines.

Tests (section 17):
- No function in `public` or `internal` uses `CURRENT_DATE`.
- An immediate cancel keeps today's delivery and removes tomorrow's, even with the session clock moved behind India.

## 2. Admin panel

These screens used the browser's clock and timezone. Orders, customers, subscriptions and reviews store UTC times without a zone, and the browser read them as local time, so a date could show 5½ hours off. An order placed at 01:00 IST appeared under the previous day.

They now use `lib/format.ts`:
- Orders: the date column, and the **NEW** badge. The badge never showed, because each order looked 5½ hours older than it was.
- Customers
- Subscriptions
- Reviews: created and updated
- Banners
- Delivery areas: start date
- Payments: transaction date and time
- Notification devices
- Daily Ops held orders: the date was raw `YYYY-MM-DD`
- Printed delivery sheets

New helpers are `formatTime` and `msSince`, with tests in `lib/__tests__/format.test.ts`.

These were already correct: `formatDate`/`formatDateTime`, `todayInIndia`, delivery-day maths and the dashboard.

## 4. Customer app

New helpers in `lib/utils/date_utils.dart`: `nowInIndia`, `todayInIndia`, `toIndiaTime`, `parseServerTimestampToIndia` and `nowForServer`. Tests are in `test/date_utils_test.dart`.

- **Wrong times on every phone (fixed).** These read stored UTC times as phone-local time, so they were 5½ hours off:
  - review dates on product pages
  - order-tracking "updated" time
  - subscription created and cancelled dates
  - user, address and category created dates
- **Wrong times saved (fixed).** Three writes sent phone-local time without a zone, so the database stored a time 5½ hours off:
  - marking notifications read (`read_at`)
  - `order_tracking.updated_at`
  - `subscriptions.cancelled_at`
  
  They now send UTC.
- **"Today" now comes from India time.** About 45 places in date logic used the phone's clock and timezone:
  - calendars and the home week strip
  - start, pause, cancel and bulk-edit pickers
  - cancellation date rules
  - "Today/Yesterday" in the wallet
  - "x ago" on notifications
  - order counts for the last 30 days
  - delivery availability for today
  
  On a phone set to India time nothing changes. On a phone set to another timezone, for example family abroad ordering for parents, the app now shows India dates. The server already decides cut-offs.
- **Order placed time and wallet times** now show in India time.
- **Left on the phone clock on purpose:** cache timers and fallbacks for a missing value.

## 5. App: notifications screen (2026-11-20)

- **Paging:** the inbox still loads 20 at a time, and the next 20 when the customer nears the bottom. It now pages by position, newest first with the id breaking ties. Before, it asked for "older than the last one shown", which skipped a notification sharing the same time at a page boundary. A repeat caused by a new notification arriving while scrolling is dropped by id.
- **Unread badge:** the home screen and the badge service ask the database for the count only. Before, they downloaded every unread row just to count them.
- **Load failure:** shows "Couldn't load notifications" with a **Try again** button. Before, it said "No notifications yet".
