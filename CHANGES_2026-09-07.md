# CHANGES — 2026-09-07

## Customer App (Hetha_app)

### Subscription product-selection rework

The create-subscription screen (`create_subscription_page.dart`) was a single
flat list that showed only product names. That is fine at four products but does
not scale as a selection task: no structure to a long list, no way to review what
has been picked without scrolling back through it, and no per-item information.

This was the last outstanding item from the 2026-08-30 tester feedback (issue 5
there), deliberately left then as a design question rather than a bug. It was
planned in this session against two confirmed facts:

- **Default is prominence, not a requirement.** The client confirmed a
  subscription need not include a "default"/essential item — only-eggs or
  only-vegetables is valid. The `is_default_sub` / `is_additional_sub` flags are
  already populated on products and are used only for UI classification: neither
  is referenced by any database function (`create_subscription`, `place_order`,
  daily-run generation), so their meaning is entirely a UX decision.
- **Products carry real `description` text**, so a details view is useful now
  rather than blocked on content.

Reworked in four parts, **all client-side — no schema, function, or data
changes.**

**1. Removed the false "must include a default product" requirement.**
`_handleCreateSubscription` blocked creation without a default-sub item, with a
hardcoded "select at least one default product (milk)" message. This was a
client-only check — the `create_subscription` RPC never enforced one — so it was
wrongly stopping valid non-staple subscriptions. Removed; creation now requires
only "at least one product". A comment records why, so it is not reintroduced as
a presumed oversight.

**2. Grouped the list into two sections.** "Daily essentials" (`default_sub`) and
"More to subscribe" (`additional_sub`), essentials first. Grouping is derived at
render time from the already-loaded list, so search and pagination are unchanged;
an empty group hides its own header (a search matching only essentials shows just
that section).

Chosen over a category-based grouping deliberately: the default/additional flags
are populated and correct today, whereas the `categories` join is not wired into
the subscription query and categories may be sparse. This gets the structure with
zero data risk. The labels avoid "Most subscribed" — that would imply popularity
data the flag does not represent, and would read false the moment a customer
subscribes to something outside that section.

**3. Added a selection review tray.** The bottom bar's bare "N items selected" is
now tappable and expands to list each pick — name, variant, `qty × price`,
running ₹/day total — each with a remove control. Height-capped at 240px so a
large selection scrolls within the tray instead of pushing the Create button off
screen; auto-collapses when the last item is removed. This is the highest-value
part at any catalog size: previously the only way to see the current selection
was to scroll back through the list hunting for selected cards.

**4. Added a read-only product details bottom sheet.** Tapping a card's
name/image opens a sheet with the larger image, full description, and all
variants with prices. A truncated one-line description preview is also shown on
the card itself.

Deliberately **not** the existing `ProductDetailsPage`: that screen is keyed on
`ProductModel` and centres one-time-purchase add-to-cart actions, which would
drop the user into cart language mid-subscription and confuse two mental models.
The sheet keeps the user in the selection context (picks, scroll position and
search all intact) and is purely informational — selection still happens only via
the variant chips on the card, so there is a single selection path.

**Not done, deliberately:** no two-step category → items flow (premature for the
catalog size; the default/additional split already provides structure), no
database changes, no reuse of the buy-now product page.

**Testing:** `flutter analyze` clean, existing suite (56) passing. No automated
tests were added — the changed logic lives inside a `ConsumerStatefulWidget`
method entangled with `setState`, Supabase and `Navigator`, with no existing test
harness for this screen; a meaningful test would require refactoring the widget
for injection first. Behaviour verified by compile; on-device visual check
recommended, specifically: an additional-only subscription creating successfully
(the previously-blocked case), the two sections with search narrowing within
them, the tray reflecting add/remove/quantity, and the details sheet clearly not
being the buy-now page.

**File:** `lib/screens/subscription/create_subscription_page.dart`

**Backend / data note:** no Supabase change. The only backend input is the
`is_default_sub` / `is_additional_sub` flags, which are managed as product data —
staples as default, the rest as additional. A product with neither flag does not
appear in the subscription list at all (the fetch filters on
`default_sub || additional_sub`).
