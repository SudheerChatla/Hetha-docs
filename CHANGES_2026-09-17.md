# CHANGES — 2026-09-17

## Customer App (Hetha_app)

All changes below are in the `Hetha_app` repo, pushed to `main` as 4 commits
(`a919951`, `8ffaff2`, `b4314c6`, `611deaf`).

### 1. Add Address button hidden behind the Android navigation bar

**Reported by:** client, testing on a real Android phone (3-button navigation).
The "Add Address" submit button was rendered partially/fully underneath the
phone's on-screen navigation bar, making it hard or impossible to tap.

**Root cause:** Android 15+ (`targetSdk` 35, which Flutter now defaults to)
enforces edge-to-edge drawing at the OS level with no opt-out — the app's
content can render underneath the system navigation bar unless explicitly
protected. The form's submit button was the last item in a plain `ListView`
with fixed padding, so on 3-button-nav devices (which reserve a much taller,
opaque bar than the thin gesture-nav inset used during development) it ended
up under the nav bar.

This is why it worked on a developer's phone (gesture nav — thin inset, easy
to miss) but failed on the client's parents' phone (3-button nav — tall,
opaque bar).

**Fix:** moved the button into `Scaffold.bottomNavigationBar`, wrapped in its
own `SafeArea`. `Scaffold.bottomNavigationBar` already reserves the correct
system-inset space on its own — the same mechanism the app's main tab bar
uses — so this is the same contract, applied consistently. The button is also
now always visible without scrolling.

**A dead end worth recording:** the first attempt fixed this with a blanket
`SafeArea` wrapped around the whole app in `MaterialApp.builder`. That
introduced a regression — it double-applied bottom padding on every screen
that *already* uses `bottomNavigationBar` (the main tab bar), showing up as a
visible extra black bar beneath it on gesture-nav devices. That global wrapper
was removed; the correct pattern is fixing each screen's own CTA placement,
not a global safety net.

### 2. Cart and Checkout: same nav-bar fix, applied proactively

An audit of the whole app (23 screens) found the same anti-pattern — a
primary action button placed as the last item in scrolling content instead of
docked at the bottom — across most screens with a submit button. Cart and
Checkout, the two highest-traffic of these, were migrated to the same fix as
the address screen:

- `cart_page.dart`: "Check Out" button (and the undeliverable-items warning
  shown above it) moved into `bottomNavigationBar`. Still only shown when the
  cart has items; all existing enable/disable logic unchanged.
- `checkout.dart`: "Pay & Place Order" / "Place Order" button moved into
  `bottomNavigationBar`. All existing conditions (payment in progress, wallet
  affordability, undeliverable items, empty cart) unchanged.

Remaining screens with the same pattern (sign-in, sign-up, wallet, edit
profile, subscription screens, and others) are not yet migrated — tracked as
follow-up, not urgent, since they were never broken by the nav-bar issue in
the same visible way Cart/Checkout/Address were.

### 3. Quantity +/- buttons on product details page hard to tap

**Reported by:** client — "when I try to tap on the plus/minus buttons, they
don't respond easily... after going to cart and back it works... or waiting a
few seconds one tap works."

**Investigation:** this turned out to be two separate things bundled into one
report:

- **Real, fixable now:** the `+`/`-` icons had only a 16×16 tappable area (the
  icon glyph's own bounding box) — genuinely easy to miss on a real thumb tap.
- **Diagnosed, deferred at the client's request:** on a slow/weak connection,
  every tap queues a real Supabase write, one at a time in strict order
  (`CartNotifier._writeQueue`), and a failed write's recovery path calls a full
  `fetchCart()` that can overwrite in-flight optimistic taps. This produces
  exactly the "waits, then one tap works, then stops" symptom on a weak
  connection. Root-caused and a fix was scoped (debounce taps into one write,
  retry-before-reconcile instead of blind refetch-on-failure, matching how
  competitor quick-commerce apps handle this), but **not implemented** — the
  decision was to leave cart-write behavior unchanged for now.

**Fix implemented today:** enlarged the tap target only. Each of `-`, the
quantity number, and `+` now has its own 44×44 circular tap target (`Material`
+ `InkWell` with `CircleBorder`), so the whole circle responds, not just the
glyph. Icon size 16→22px, quantity number 12→18px bold, pill height 40→48px.
Disabled state (e.g. `-` at qty 0) now visibly dims. No changes to
`addToCart`/`removeFromCart` or the cart provider's write/retry behavior.

### 4. Home tab: unnecessary refetching on every tab switch

**Investigation prompted by a question, not a bug report** — asked whether the
address shown on Home is fetched fresh every time the Home tab is visited.

**Finding:** yes — returning to the Home tab from any other tab
(Cart/Orders/Wallet/etc.) called `_initializeData()` in full, which
unconditionally invalidated `bestSellerProductsProvider` and
`categoriesProvider`, and called `userAddressesProvider(...).refresh()` — a
real Supabase round-trip for all three, on every single tab switch, regardless
of whether anything had changed. On a weak/roaming connection this adds
avoidable delay and load for no benefit, since:

- Any address add/edit/delete already updates the shared in-memory provider
  directly (confirmed via `UserAddressesNotifier` — every mutation method
  writes to `state` immediately; nothing needs a refetch to see the result
  elsewhere in the app).
- Categories and best-sellers are admin-managed catalog data with no in-app
  customer action that changes them — session-level staleness is an accepted
  tradeoff, not a defect, for this kind of content.

**Fix:** returning to the Home tab no longer triggers this full refresh — it
now only refreshes the notification unread-count badge (the one thing that
can genuinely change while on another tab). The full refresh (addresses,
best-sellers, categories) still happens on first app load and on
pull-to-refresh, which remains the manual override if a customer wants the
absolute latest catalog data mid-session.

### 5. First/second subscription not appearing on Home until app restart

**Reported by:** client — after successfully creating a subscription, the
Home calendar stayed on "No active subscriptions" until the app was fully
closed and reopened.

**Root cause:** `CreateSubscriptionPage` already invalidates
`userActiveSubscriptionsProvider` on success, and `SubscriptionListPage`'s own
"Start Subscription" entry point already reacts to that correctly. But Home's
two navigation paths into that flow — the empty-calendar card's tap, and the
"View All" link — were plain `Navigator.push(...)` calls with no `.then(...)`
handler, so Home itself was never told to re-fetch when control returned to
it. Home is kept alive in `MainWrapper`'s `IndexedStack` (rather than rebuilt
from scratch on every tab visit), so it had no other trigger to pick up the
change short of a full cold start — which is exactly the symptom reported.

**Fix:** both of Home's navigation calls into `SubscriptionListPage` now do
`.then((_) => ref.invalidate(userActiveSubscriptionsProvider))` on return,
matching the pattern already used correctly elsewhere in the same file
(`_buildSingleSubCalendar`'s own tap handler). This applies equally to a
second, third, etc. subscription — the fix is generic to "returning to Home
after visiting the subscription list/create flow," not specific to the
first-ever subscription.

### 6. Empty-calendar card visual consistency

Minor follow-on from item 5's investigation: the "No active subscriptions"
card and the populated calendar card were already pinned to identical
height/width/background/padding (deliberately, to avoid a layout jump when a
subscription loads in), but a narrow centered-text column read as more
"square/boxy" next to the populated view's full-width day-row. Added
`width: double.infinity` and explicit text centering so the empty state's
content claims the same horizontal footprint as the populated one.
