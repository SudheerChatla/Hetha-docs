## 1. Problem: the Wallet tab showed a stale snapshot

`Hetha_app/lib/screens/wallet/walletpage.dart` loaded its data once, in
`initState`. The bottom tabs are kept alive in an `IndexedStack`
(`main_wrapper.dart`), so `initState` runs **once per app session**. Nothing
else reloaded the page.

### Before

| Trigger | Balance + days left | Transactions |
|---|---|---|
| First visit to the Wallet tab | ✅ | ✅ |
| Later visits to the tab | ❌ | ❌ |
| Top-up from this screen | ✅ | ✅ |
| Refresh icon | ❌ balance not refreshed | ✅ |
| Pull-to-refresh | ❌ not implemented | ❌ |
| App returns from background | ❌ | ❌ |
| Any database change | ❌ no listener | ❌ |

Missed changes, all of which change `wallet_balance` and add a
`wallet_transactions` row:
- daily subscription deduction;
- wallet payment for a one-time order at checkout;
- refunds (cancellation, short delivery via `record_order_delivery`);
- admin wallet credit or debit;
- a top-up made from another screen.

Changes to subscriptions (new, paused, cancelled, quantity) were also missed,
which the "days left" and per-day figures depend on.

### Example
1. Customer opens Wallet: **₹1,000**, "10 days left".
2. Pays ₹300 from the wallet at Checkout. Home shows **₹700** (Home uses the
   live stream).
3. Back on the Wallet tab: still **₹1,000**, and no ₹300 transaction.
4. Taps refresh: the transaction appears, but the balance stays **₹1,000**.
5. Only an app restart fixed it.

Other routes to the same problem: Create Subscription's low-balance top-up and
a "wallet" push notification each open a **separate** wallet screen
(`pushNamed('/wallet')`). That copy loaded fresh, but the tab behind it stayed
stale.

### Also found
- `setState` called without a `mounted` check after the balance query: a
  "setState() called after dispose()" error if the screen closed mid-load.
- A comment in `lib/services/notification_service.dart` claimed the wallet
  screen kept itself current through its own `.stream()` on `users`. It
  didn't.

## 2. Options considered

| | A: use the existing stream (**chosen**) | B: no realtime |
|---|---|---|
| Balance updates | Instantly, even with the tab open | On tab open, pull-to-refresh, resume |
| Extra Supabase cost | None: `userDataProvider` is already open for every logged-in customer | One query per tab open |
| Matches Home / Checkout | Always | Can differ while the tab is open |

Option A was chosen: no new cost, the same balance everywhere, and it catches
changes made while the tab is open (for example an admin credit).

## 3. Fix

**`lib/screens/wallet/walletpage.dart`**

| Change | Detail |
|---|---|
| Follows the live balance | Now a `ConsumerStatefulWidget`; `ref.listenManual(userDataProvider, …)` in `initState`. This is the same `.stream()` on the customer's own `users` row that Home, Checkout and Subscriptions use: no new connection or channel. |
| Refetch on money movement | When `wallet_balance` changes, the balance shows at once and transactions + days-left are re-fetched after a 400 ms debounce. Every wallet movement goes through `internal.apply_wallet_delta`, so a balance change also means a new transaction row. Profile edits on the same stream are ignored. |
| No double load on open | The stream's first value only sets the balance; the initial load already fetched everything else. |
| One refresh at a time | `_refreshAll()` runs the balance and transaction queries together. If one is already running, it re-runs once afterwards instead of overlapping. |
| Resume from background | Reuses `ResumeRefreshPolicy` (20 s threshold, same as the Orders screen). Realtime does not replay events missed in the background. |
| Pull-to-refresh | On the transaction list area, including when it's empty. Reloads balance and days-left as well. |
| Refresh icon | Now reloads everything (was transactions only); tooltip "Refresh". |
| After a top-up | Uses `_refreshAll()`, which also covers a dropped Realtime connection. |
| `mounted` guards | Added before every `setState` in both fetches; the error path now logs. |

**`lib/utils/wallet_stream_action.dart` (new):** the "what to do on a stream
event" rule (`ignore` / `showBalance` / `showBalanceAndRefetch`), kept out of
the widget so it can be unit-tested. This follows the pattern of
`ResumeRefreshPolicy`.

**`test/wallet_stream_action_test.dart` (new):** 6 tests:
- no balance yet → ignore;
- first value → show, no refetch;
- same balance (profile edit) → ignore;
- debit, credit, and drop to zero → refetch.

**`lib/services/notification_service.dart`:** the comment now describes what
the wallet screen actually does.

**⏳ Manual test on a device** (Realtime can't be exercised by unit tests):
1. Open the Wallet tab and note the balance.
2. Admin panel → Customers → this customer → Wallet → credit ₹10. The balance
   updates within a second or two without leaving the tab, and the new
   transaction appears.
3. Place a wallet-paid order, then return to the Wallet tab. The balance is
   lower and the order transaction is listed.
4. Background the app for more than 20 s, make an admin credit meanwhile, and
   reopen the app. The Wallet tab shows it.
5. Pull down on the transaction list: the spinner shows and everything reloads.
