## 8. Migration 038: Daily Ops structure

`docs/db/migrations/038_daily_ops_structure.sql`

| Object | What it does |
|---|---|
| `internal.subscription_delivers_on(sub, date)` | The delivery-day rule, once (same as the old TypeScript generator): move-away → no; paused → no; move-onto skips start/end/cadence; area cadence (or swap-borrowed area) when frequency > 1 with a reference date, else the subscription's own frequency; at least one active item. |
| `internal.subscription_items_on(sub, date)` | The items that go out that day. |
| `generate_daily_run(date, admin)` | Generation in one transaction, no row cap, refused on a finalized/reconciled date. Rebuilds only untouched orders. |
| `add_daily_order_item` / `remove_daily_order_item` / `set_daily_order_item_quantity` | Staff item edits on a draft day, priced from the catalog; removing the last item of a paid order cancels and refunds it. |
| Finalized-day lock (two triggers) | Payment/finalize fields change only inside the Daily Ops functions; finalized order: only note and route; its items: only `delivered_qty` 0 … quantity; nothing on a reconciled day; no paid inserts, none onto a finalized day. |
| `get_earliest_change_date(sub)` | The cut-off date for the app (M-01). |

**Deviations from the plan (all deliberate):**
- **Trusted-function flag — corrected.** The first version attached
  `SET hetha.daily_ops_rpc = 'on'` to each function (`ALTER FUNCTION`). Applying
  it in the Supabase SQL Editor failed with
  `42501: permission denied to set parameter "hetha.daily_ops_rpc"` (the
  `postgres` role is not a full superuser; the test database is, so the suite
  did not see it). Nothing was applied (one transaction). 038 now does what the
  plan said: each trusted function starts with
  `PERFORM set_config('hetha.daily_ops_rpc', 'on', true);` and the seven 037
  functions are re-declared with their bodies copied unchanged plus that line
  (copied by script, not by hand). A new test fails if any migration from 038
  on attaches a `hetha.*` setting to a function. ⚠️ A later migration that
  re-declares one of these functions must keep the `set_config` line.
- **`claim_adhoc_user` cascade.** Re-keying a walk-in customer updates
  `user_id` on their orders (`ON UPDATE CASCADE`). The lock allows a `user_id`
  change on a finalized order only when the old user row is gone, so that
  cascade works and a hand edit does not.
- **Insert guard added.** The plan guarded UPDATE/DELETE only. A direct insert
  of an already-paid order would let a later cancel refund money that was never
  taken, so inserts must be unpaid/unfinalized and not onto a finalized day.
  Customer functions already insert that way.
- **`generated` on a second run is not 0.** Clean orders are deleted and
  rebuilt every run (plan step 6), so the count includes them. The test checks
  the real guarantee: never two orders for one subscription and date.

**Test harness changes:** `as()` / `asQuery()` now clear the caller's claims
after each call, so plain setup writes run as the SQL Editor; the suite
re-applies 038 after its two re-runs of 037 (037 re-declares its functions,
which drops the flag).
