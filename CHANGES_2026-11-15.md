## 2. B-01: verify:018 passes

**Problem.** The 018 harness loads `functions.sql` (post-032, where
`claim_adhoc_user` has a 6th argument `p_adhoc_id`) and then replays migrations
up to 018, which create the old 5-argument version. Two overloads → the
5-argument call was "not unique". Live never has both (032 drops the old one).

**Fix.** `docs/db/tests/verify_018_drop_legacy_user_columns.mjs` drops the
6-argument overload right after loading the snapshot, so the harness models the
pre-032 database it is testing. No migration or snapshot changed.

## 4. A-02: no state updates during render

- **Daily Ops** (`useDailyOps.ts`, `RunSheetTab.tsx`, `page.tsx`, `types.ts`):
  `initItemDraft` / `initOrderDraft` (called while rendering) removed. The
  delivered-quantity and note boxes are seeded once in `fetchOrders`. A stored
  `0` shows as `0`; a missing quantity stays blank (D-7).
- **Deliveries** (`app/admin/deliveries/page.tsx`): `initDeliveryDraft`
  (called while rendering) removed. Saving builds the quantities from what
  staff typed, else the stored delivered quantity, else the ordered quantity.
  The boxes show the same fallback.
- **Deviations from the plan:**
  - Step 4 asked for a `useEffect` that seeds drafts. eslint-plugin-react-hooks
    7 rejects state updates in an effect (`set-state-in-effect`), so the
    quantities are computed when needed instead. Same behaviour.
  - Step 5 (`isExpanded || true` → separate print block) **not done**. The
    current block already hides collapsed stops on screen and shows them in
    print; the plan's version renders the same content in two places for the
    same result.

## 5. P1-01: list of missing delivered quantities

Clicking **Reconcile** first reads the whole day (without the run-sheet
filters) and, if any pending order has an item with no delivered quantity,
opens **Delivered quantities still needed** (customer, phone, route, items)
instead of sending the request. The amber banner on the Reconciliation tab has
a **View list** button. A recorded `0` is not listed. If the database still
refuses because someone changed an order meanwhile, the list is refreshed.
The filter is a pure function, `app/admin/daily-ops/lib/missingQuantities.ts`
(ready for the B-03 test). No SQL changed.

Deviation: the plan says to reopen the list on any error starting with
`Cannot reconcile:`. That prefix is also used for "date is draft", so the
check matches `no delivered quantity` instead.

## 6. P1-02: cancelled orders audit

Read every admin query and total over `subscription_daily_orders`. No change
was needed:
- `getDeliveries` skips skipped/cancelled daily orders; one-time `cancelled`
  orders are excluded. The page refetches after a save; no optimistic re-add.
- Run-sheet value/count, Live Status, route sheets and CSV export use
  `isGoingOut`; delivered counts use `status = 'delivered'`.
- No dashboard, customer or payments code reads daily orders, so no revenue
  figure uses `total_value`. Refunds show in the customer's wallet history.
- Reconciliation renders cancelled orders with the status dropdown enabled
  until the day is reconciled.
- No new delete of `subscription_daily_orders` / `wallet_transactions`.
