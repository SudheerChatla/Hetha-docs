## Session goal

Audit both `Hetha_admin` and `Hetha_app`, surface issues, and start fixing the
most impactful ones — focusing on:

- Bringing the admin-created ad-hoc user flow into parity with the app-native
  user flow (so they share the same code paths, same RPCs, same data shape).
- Closing real security holes in the admin (no auth checks on API routes,
  middleware never runs, admin-creating-admin session stealing, etc.).
- Migrating the Flutter app off Firebase entirely (Auth was already on
  Supabase; database, storage, and tracking were the remaining touchpoints).

## Completed — Hetha_admin

### Ad-hoc page parity work

#### 1. Address modal improvements

- Added `landmark` text input, `address_type` selector (home / work / other),
  and an `is_default` checkbox to `AddAddressModal`.
- Phone and pincode inputs now strip non-digits on entry.
- Address card on the detail panel now shows the `address_type` chip and the
  landmark line in addition to the default badge.
- `addCustomerAddress` in `services/customerService.ts` now mirrors the
  Flutter app's `addAddress` logic: if it's the user's first address it
  forces `is_default = true`, and if `is_default` is being set it clears
  `is_default` on all other rows for that user first.

> **Why:** the admin form had `address_type` and `is_default` hardcoded; ad-hoc
> users could end up with no default address, which the app then handles
> inconsistently.

#### 2. Atomic initial wallet credit

- `createCustomer` now inserts the user with `wallet_balance: 0`, then applies
  any requested initial balance via the `update_wallet_balance` RPC. Single
  atomic path — `users.wallet_balance` and `wallet_transactions` can no longer
  drift. If the RPC fails, the user row is rolled back.

> **Before:** two separate writes (insert user with balance, then insert a
> wallet_transactions row). If the second write failed, balance ≠
> sum(transactions) forever.

#### 3. Convention standardization

- `wallet_transactions.initiated_by` now consistently writes the **role
  string** (`'admin'`), not a UUID. The acting admin's UUID is appended to
  the description for audit context.
- `users.language` standardized on the ISO-639-1 code (`'en'`, `'hi'`).
- Sign-in now writes `'en'`. Settings page reads ISO codes with a
  backwards-compat normalizer for legacy `'English'` / `'Hindi'` values.

#### 4. `createAdHocOrder` now goes through `place_order` RPC

- Admin ad-hoc orders use the same RPC the Flutter app uses, so:
  - Order numbers are `HET-<timestamp>` (same as app orders).
  - Wallet deduction is atomic (RPC handles the row lock).
  - Canonical prices/labels come from `product_variants` server-side — admin
    can no longer manipulate prices client-side.

> **Before:** four separate writes, no transaction; could leave order placed
> but unpaid if the wallet RPC failed at the end. Order numbers used a
> different `AH-` prefix that broke any reports filtering on `HET-%`.

#### 5. `createAdHocSubscription` now goes through `create_subscription` RPC

- Same RPC the app uses. Behaviors inherited:
  - Cancels any currently-active subscription for that user (one-active-sub
    rule is now enforced on the admin path too).
  - `delivary_area` and `delivary_frequency` are derived from the address
    pincode; admin **cannot override** them. Per user request: "delivery
    frequency should be the one which is there for area only — uniformity,
    no confusion."
- Admin-only fields (`route_id`, `payment_method`, `address_id`) are patched
  on the new row right after the RPC returns.

#### 6. Pre-existing TypeScript errors fixed

Four errors flagged in the original audit, now all gone:

- `app/api/admin/delivery-charges/[id]/route.ts` — was using sync
  `params: { id: string }` instead of the async `Promise<{ id: string }>`
  shape Next.js 15+ requires. **This was an actual runtime bug** — admin
  edit/delete of delivery charge tiers was silently failing.
- `app/api/admin/ad-hoc/route.ts`, `delivery/route.ts`, `settings/route.ts` —
  empty stub files with zero callers, deleted.

#### 7. Ad-hoc → app-user conversion (Option A)

The biggest piece. Three commits:

**Commit 1 — DB migration**

- File: `Hetha_app/doc-schema/migrations/2026_05_25_claim_adhoc_user.sql`
- Reissued every FK that references `public.users(id)` with `ON UPDATE
  CASCADE` (8 FKs across `addresses`, `cart_items`, `notifications`,
  `orders`, `reviews`, `subscription_daily_orders`, `subscriptions`,
  `wallet_transactions`).
- Created `claim_adhoc_user(p_auth_uid, p_email, p_phone, p_first_name,
  p_last_name)` RPC. Four branches:
  1. Returning user → no-op.
  2. Ad-hoc row matches by email or phone → claim it (id reassigned to the
     new auth UID, `is_adhoc` flips false; cascading FKs carry every child
     row to the new id).
  3. A non-ad-hoc row already exists with same email/phone but different id
     → raise `unique_violation` with a clear error message.
  4. Otherwise → fresh insert.
- `EXECUTE` granted to `authenticated` only.
- **Migration applied successfully on 2026-05-25.** Verified with the FK
  audit query — all 8 FKs reported `on_update = CASCADE`.

**Commit 2 — Flutter sign-in updated**

- `lib/screens/auth/sign_in_page.dart` no longer does its own
  check-then-insert. It calls `claim_adhoc_user` once per sign-in. On
  collision (different account already exists with same email/phone) the
  user is signed out and shown a clear error.

**Commit 3 — Admin "Convert to App User" button**

- New env var required: `SUPABASE_SERVICE_ROLE_KEY` (server-only, never
  prefixed `NEXT_PUBLIC_`).
- New file `Hetha_admin/lib/admin-client.ts` — service-role client factory.
- New route `POST /api/admin/customers/[id]/convert-to-app-user` —
  privileged: creates the auth user via `auth.admin.createUser`, then runs
  `claim_adhoc_user`, rolls back the auth user if the claim fails.
- New `ConvertToAppUserModal` in the ad-hoc page detail panel. Auto-generates
  random password (uses `crypto.getRandomValues`), copy-to-clipboard, eye
  toggle. Shown only when `selectedCustomer.is_adhoc === true`.
- **End-to-end manual test passed.**

### Tier A — security/correctness

#### A1. Auth + permission check on every admin API route

- New helper `Hetha_admin/lib/api-auth.ts:requireAdmin(perm)`. Returns
  either `{ supabase, userId, permissions }` or a `NextResponse` with the
  right 401/403.
- Applied to **all 21 admin API routes** plus the convert-to-app-user route.
  Permissions mapped to the existing `PAGE_PERMISSIONS` keys (or
  `super_admin` for access-control).

> **Before:** every `/api/admin/*` route only did `createActionClient()` and
> trusted whoever had a Supabase session. RLS was the sole defense. Any
> signed-in customer could hit those endpoints directly.

#### A2. Middleware actually runs now

- Renamed `proxy.ts` → `middleware.ts` (the canonical Next.js name).
- `proxy.ts` was dead code — Next.js auto-discovers middleware by file name.

#### A3. Admin creating admin no longer steals the acting admin's session

- `accessControlService.createAdminUser` switched from
  `supabase.auth.signUp(...)` (cookie-bound, replaces session) to
  `createAdminClient().auth.admin.createUser(...)` (server-side admin API,
  no session impact).
- Added password length validation (≥ 8). Errors mapped (409 for "already
  exists" cases). Auth user rolled back if `assignRole` fails afterward.

#### A4. Search input sanitized before `.or()` interpolation

- New helper `Hetha_admin/lib/sanitize.ts:sanitizeSearchTerm` strips
  PostgREST delimiters (`,`, `(`, `)`, `"`, `\`), collapses whitespace, and
  caps length at 100 chars.
- Applied at all 7 call sites (`searchUsers` × 2, `getPaginatedCustomers`,
  `getNewCustomers`, `getSubscriptions`, `getNewSubscriptions`,
  `getWalletTransactions`).

### Tier B — UX & pattern consistency

#### B1. Route/area validation in `CreateSubModal`

- On modal open, fetches `/api/admin/delivery-areas` (with pincodes joined).
- Derives the area from the selected address's pincode (same lookup the
  RPC does internally).
- Route dropdown shows only routes whose `area_id` matches.
- Three feedback states: pincode unserved (red panel), area resolved with
  no active routes (amber panel), area resolved with routes (grey hint).
- Submit gated on area resolution + route picked + items selected.

#### B2. Pincode + delivery-charge validation in `CreateOrderModal`

- Same pincode → area resolution as B1.
- On modal open, also fetches `/api/admin/delivery-charges` (tier table).
- Total cart weight computed from `variant.weight_grams × quantity`.
- Matching `delivery_charge_tier` is resolved by weight band; the resulting
  charge is shown in a Subtotal / Delivery / Total breakdown.
- `delivery_charge` now sent in the POST body (was always 0 before).
- Submit gated on area resolution + items present + tier matches.

#### B3. Permission key drift fixed

- `RouteGuard` `PAGE_ROUTES`:
  - `/admin/access-control` now requires `super_admin` (was `admin:view`,
    which didn't exist anywhere).
  - `/admin/ad-hoc` now requires `customers:view` (was `users:view`, which
    didn't exist anywhere).
  - Removed dead entries for `/admin/reviews`, `/admin/pincodes`,
    `/admin/delivery` — none of these page routes exist any more.
  - Added previously-missing entries for `/admin/delivery-areas` and
    `/admin/delivery-charges`. These pages were completely unguarded
    before — any authenticated session could navigate to them.
- `AdminSidebar` ad-hoc link's `reqPerm` updated to `customers:view`.

## Completed — Hetha_app (Flutter)

### Settings page now writes to Supabase, not Firestore

- `lib/screens/profile/settings_page.dart` was reading/writing
  `notifications` / `language` / `darkMode` to a Firestore `users/{id}`
  document — completely disconnected from the Supabase `public.users` row
  the rest of the app reads from.
- Migrated to Supabase. Reads/writes `users.notifications_enabled`,
  `users.language`, `users.dark_mode`. Language picker now stores ISO
  codes with a display-label map and a backward-compat normalizer for
  legacy `'English'` / `'Hindi'` values.

### Sign-in now uses `claim_adhoc_user` RPC

- `lib/screens/auth/sign_in_page.dart` replaced the manual
  check-then-insert with a single RPC call. On collision (someone else
  already has an account with the same email/phone), the user is signed
  out and shown a friendly error.

### Order tracking migrated from Firestore to Supabase

- `lib/models/order_tracking.dart` rewritten — dropped `cloud_firestore`
  / `Timestamp`, now uses plain `DateTime` parsing. `fromMap` accepts
  either snake_case (raw Supabase rows) or camelCase (legacy
  `_mapOrderData` wrapper).
- `lib/services/order_tracking_service.dart` now reads/writes the Supabase
  `public.order_tracking` table. URL-building helpers (`generateTrackingUrl`,
  `launchTrackingUrl`) kept as pure utilities.
- `lib/services/order_service.dart:_mapOrderData` now also forwards
  `orderId`, `mobileNumber` (from `orders.snapshot_phone`), and
  `customerMessage` so `OrderTracking.fromMap` has complete data. **This
  fixed a real bug** — the old fromMap did `map['orderId'] as String`
  which would have crashed for any tracking object built from that map.

### Reviews migrated from Firestore to Supabase

- `lib/screens/orders/review_page.dart` now uses the Supabase
  `public.reviews` table. Maps form fields onto actual columns
  (`user_id`, `product_id`, `order_id`, `rating`, `description`).
- Dropped the Firestore-only fields (`productName`, `userEmail`,
  `updatedAt`). The "edit existing review" semantic preserved by
  matching `(user_id, product_id, order_id)`.

### Edit Profile migrated from Firestore to Supabase

- `lib/screens/profile/edit_profile_page.dart` now updates
  `public.users.first_name` / `last_name` (single-name input split on
  whitespace). Auth metadata is also synced via `auth.updateUser` so
  anything reading `user.userMetadata['fullName']` updates without a refresh.

### Cart page stale import removed

- `lib/screens/cart/cart_page.dart` had an unused `cloud_firestore`
  import, deleted.

### Firebase removed entirely

After migrating the four touchpoints above, Firebase was no longer used.

- `pubspec.yaml` — dropped `firebase_core`, `firebase_auth`,
  `cloud_firestore`, `firebase_storage`.
- `lib/main.dart` — removed Firebase imports, removed
  `Firebase.initializeApp(...)` call, removed dead-code subscription
  scheduler comments.
- Deleted `lib/firebase_options.dart`, `firebase.json`, `.firebaserc`.
- `flutter pub get` regenerated `windows/flutter/generated_plugin_*`
  without Firebase entries automatically.
- `lib/widgets/firebase_storage_image.dart` — class kept (renaming would
  touch 3 screen imports), but the doc comment now clarifies the class
  doesn't actually use the `firebase_storage` package; it's just
  `cached_network_image` and `Image.asset`.

> **No platform-side cleanup needed** — there was no `google-services.json`
> in `android/app/` and no `GoogleService-Info.plist` in `ios/Runner/`.
> The app was running Firebase entirely via dart-side options pulled
> from `.env`.

> **Bundle / startup impact (estimated):**
> - Android APK: ~8–12 MB smaller
> - iOS IPA: ~5–8 MB smaller
> - Cold-start: ~200–400 ms faster

### Tier A bug fixes (A1, A2)

- **A1.** `order_service.dart:_mapOrderData` no longer crashes on a NULL
  or non-string `placed_at`. Uses `DateTime.tryParse` with a `DateTime.now()`
  fallback. Previously the entire orders page would crash for any user
  whose history contained an order with a missing `placed_at` (possible
  for `payment_pending` rows before the trigger fires).
- **A2.** `subscription_service.dart` no longer wraps mutations in
  `_executeWithRetry`. The helper itself is gone. `createSubscription`,
  `updateSubscription`, `cancelSubscription`,
  `cancelSubscriptionWithCustomDate`, `saveDailyOrder`, and
  `deleteDailyOrder` now surface their first failure directly. Reasons:
  retries amplified DB load on already-failing requests, produced
  confusing duplicate audit log entries when both attempts wrote, and
  hid the real error from the user.

### Tier B fixes (B1, B2, B4, B5, B7, B8, B9)

- **B1.** `splash_screen.dart` — the legacy `Text('HETHA App', ...)`
  underneath the logo had `color: Colors.white` on a white background, so
  it was invisible in production. The first pass made it visible by
  switching to brand brown `#865B33`, but the user later asked for the
  text to be removed entirely. Final state: splash shows only the logo
  with the existing fade-in animation; the Text widget and its spacing
  are gone.
- **B2.** `main.dart`:
  - Removed deprecated `primarySwatch: Colors.blue` (silently ignored
    under M3 with `colorScheme: ColorScheme.fromSeed`). Stays removed.
  - **Seed color: reverted.** The first pass switched the seed from
    `Colors.deepPurple` to brand brown `#865B33` to match the auth/profile
    cream-brown palette, but the user reported the resulting orange/tan
    accents on Material 3 widgets (FAB, ripple, chips, app bar tints)
    didn't match their expectation. **Final state: seed is back to
    `Colors.deepPurple`** so all Material accents render in the
    purple-family palette they had before this session.
  - `AuthWrapper` `Future.delayed(2 seconds, ...)` now bails with
    `if (!mounted) return;` before calling `setState`, fixing a
    potential crash when the user kills the app within 2 s of opening.
    Stays.
  - Removed dead `home_page.dart` import (the `/home` route uses
    `MainWrapper`, never `HomePage` directly). Stays.
- **B4.** `delivery_area_service.dart` — TTL on the static cache
  shortened from **1 hour to 5 minutes** so admin-side changes propagate
  to customer apps quickly. Added a public static `invalidateCache()`
  for explicit refreshes (e.g. from a future Supabase realtime listener).
- **B5.** `user_area_service.isDeliveryAvailableForUser` no longer
  hardcodes `['Delhi', 'Noida', 'Ghaziabad']`. Now calls
  `DeliveryAreaService.getAllActiveAreas()` and does a case-insensitive
  match. New active areas the admin adds in `/admin/delivery-areas`
  immediately work in the customer app.
- **B7.** `delivery_charge_service.dart` — N+1 fixed. Collects all
  variant ids and fetches in **one** `.in()` query, then computes
  weighted total from the resulting map. Previously issued one
  round-trip per cart item. Replaced `print` with `debugPrint` while
  here.
- **B8.** `subscription_address_service.storeAddressForNewSubscription`
  no longer mirrors `area`/`pincode` back onto `public.users`. The
  subscription snapshot is the source of truth; mirroring caused the
  two locations to drift after later edits. The function still validates
  the address against the active delivery areas before returning.
- **B9.** `address.dart` model — `addressType` normalized to lowercase
  end-to-end. Constructor default and `Address.empty()` use `'home'`.
  `fromMap` lowercases on read so legacy `'Home'`/`'Work'`/`'Other'`
  rows surface as `'home'`/`'work'`/`'other'`. `toMap` lowercases on
  write. UI code comparing against `'home'` etc. now works for both
  legacy and fresh rows. Optional one-time DB cleanup later:
  `UPDATE addresses SET address_type = lower(address_type) WHERE address_type ~ '[A-Z]';`

## Pending — Hetha_admin

These items came up in the audit but were not addressed today.

### Code-quality / hygiene

- **Empty admin dashboard.** `app/admin/page.tsx` returns `<></>` with a
  defined-but-unused `handleLogout`. Anyone landing on `/admin` after login
  sees a blank page. Surface a few summary cards (today's order count,

- **Production `console.log` calls.** ~70 of them across the codebase.
  Replace with structured logging or remove. (Some were already removed
  during the A1 work — products and subscriptions routes — but many remain.)
- **Pervasive `any` types.** ~200 sites across the admin codebase. Worth a
  slow-burn cleanup, low risk per file. Best done one service at a time.
- **`next.config.ts` is empty.** No image-domain whitelist, no security
  headers (`Strict-Transport-Security`, `X-Content-Type-Options`,
  `X-Frame-Options`, `Content-Security-Policy`). Worth adding the standard
  set.
- **Branding inconsistency** — `pubspec.yaml: name: hetha_organics`,
  `main.dart: title: 'Hetha App'`, `sign_up_page.dart: 'HETHA App'`,
  admin says `'Hetha Admin'`. Pick one canonical name.

### Decisions / further unification

- **Route/area mismatch warning** when admin picks a route from a different
  area than the address pincode resolves to. Currently `CreateSubModal`
  filters routes by area (B1) — but admin could in theory still create a
  subscription via API with a mismatched route_id. Adding a server-side
  check in `createAdHocSubscription` would harden this.
- **Allowing super_admin to demote themselves carefully.** The existing
  `assignRole` protection logic is correct in effect (won't let the last
  super admin be removed) but the variable naming inside the function is
  misleading (`authUserId = userId` where `userId` is actually the target,
  not the actor). Rename for clarity.
- **`searchUsers` `.or()` on embedded relations** — admin search uses
  `subscription_items.product_name_snapshot.ilike.%X%` inside `.or()` on
  the parent `subscriptions` query. PostgREST may or may not support this
  syntax depending on version. Worth verifying with real data and possibly
  switching to a server-side RPC if it's flaky.

## Pending — Hetha_app (Flutter)

The Flutter audit produced findings in four tiers. Tier A items A1 and A2
were addressed today, and most of Tier B is now done. Remaining work:

### Tier A — real bugs to fix soon

1. **`address_service.dart:deleteAddress` `firstWhere` without `orElse`** —
   throws `StateError` if the cache is stale and the address isn't in the
   local list. Replace with `firstWhereOrNull` or `try/catch`.
2. **`address_service.dart:updateAddress` default-management race** —
   `_clearOtherDefaults(userId)` runs before the update if `address.isDefault`,
   leaving a brief window with zero defaults. Wrap in an RPC for atomicity.
3. **`subscription_scheduler.dart` is the wrong design pattern** — runs an
   in-app `Timer` to process pending cancellations for **all** users,
   under the current customer's auth context. Already commented out in
   `main.dart` so it's not running, but the file should be deleted to avoid
   future confusion. Replace with a Supabase scheduled function (pg_cron).

### Tier B — UX & maintainability (mostly done; remainder)

- **B6. `pause_service.dart` non-atomic loops** — many sequential
  supabase calls per pause/resume. Half-applied state is possible if the
  network drops mid-loop. Build a Postgres function `replace_pauses(...)`
  that handles the merge/split logic in one transaction. **Not addressed
  today** because it requires writing and reviewing PL/pgSQL that
  reproduces the existing merge/split logic — best handled as its own
  migration with focused review.
- **B10. Bundle IDs are still placeholders** — `.env` has
  `IOS_BUNDLE_ID=com.example.frontend` and the same for macOS. App Store
  Connect will reject this. Set to `com.hetha.organics` (or the registered
  ID). **Not addressed today** because the canonical value depends on the
  Apple/Play Store registration and we needed user input on what to use.

### Tier C — cleanup / hygiene

- **C1. `analysis_options.yaml` corrupted.** First line is
  `Remuneration: Half - TAship as per Insititute Norms# This file ...`.
  Two-second fix.
- **C2. Dead code to delete.**
  - `order_service.dart:createTestOrder` — throws `UnimplementedError`.
  - `cart_service.dart:fetchCart` — superseded by `fetchCartWithDetails`.
  - `subscription_scheduler.dart` — flawed design (see Tier A item 3).
- **C3. `response == null` defensive checks** after `.select()` —
  Supabase returns an empty list, never null. Dead branches in
  `product_service.dart`, `address_service.dart`, etc.
- **C4. ~~`delivery_charge_service.dart` uses `print()`~~** — fixed today
  as part of B7. Now uses `debugPrint`.
- **C5. Outdated dependencies in `pubspec.yaml`.**
  - `intl: ^0.18.0` (current 0.20.x).
  - `flutter_riverpod: ^2.4.9` and `riverpod_annotation: ^2.3.3`
    (Riverpod 3.x is out).
  - Several others stale. 103 packages reported newer versions
    incompatible with current constraints.
- **C7. Three big screen files** — `subscription_page.dart` 116 KB,
  `subscription_day.dart` 84 KB, `home_page.dart` 46 KB,
  `walletpage.dart` 44 KB, `bulk_modify_subscription.dart` 42 KB.
  Almost certainly mix UI, business logic, state. Worth scheduling a week
  to refactor.
- Many `withOpacity` usages — deprecated in Flutter 3.32; should migrate
  to `.withValues()`.

### Tier D — design questions to decide

- **D1. Razorpay edge function: atomicity of wallet recharge.**
  `supabase/functions/razorpay/index.ts` does read → compute → write →
  insert for the wallet update. Two simultaneous successful Razorpay
  payments by the same user could both read the same balance, lose one
  credit. Replace with the existing `update_wallet_balance` RPC.
- **D2. Sign-up flow doesn't capture phone.** `sign_up_page.dart` only
  collects email + password + name. Means the auto-claim path matches by
  email only. If admin only had the customer's phone (no email) when
  creating the ad-hoc, the customer signing up via the app can't be
  auto-claimed.
- **D3. `addressType` casing.** See B9 — needs a one-time decision plus
  small migration: `UPDATE addresses SET address_type = lower(address_type)`.
- **D4. Scheduler placement.** Tier A item 3 noted the in-app scheduler is
  wrong.
  Replace with `pg_cron` (Supabase scheduled function), Edge Function with
  cron trigger, or accept manual processing for now.
- **Remaining Firestore migration item (now done as part of today's
  Firebase removal):** all done — no Firestore touchpoints remain.
