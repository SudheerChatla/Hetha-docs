# CHANGES — 2026-08-24

## Customer App (Hetha_app)

### 1. Realtime Auto-Refresh for Orders

The orders list and order details screens previously only refreshed via
pull-to-refresh — a newly placed order, or a status change made from the
admin panel, was invisible until the customer manually reloaded.

**Root cause:** no `postgres_changes` subscription existed on either screen.
`getRawUserOrdersFuture()` is a one-shot `Future`, not a stream (streams had
been deliberately removed earlier to avoid a `RealtimeSubscribeException`
timeout caused by leaked channels — see comment in `order_service.dart`).

**Fix:**
- `order_page.dart`: opens one Realtime channel (`user-orders-<userId>`)
  with two `postgres_changes` listeners — `orders` filtered to
  `user_id = auth.uid()`, and `order_tracking` (unfiltered, no `user_id`
  column to filter on). Any insert/update/delete triggers a debounced
  (400ms) refetch of the order list. Channel is always removed in
  `dispose()` to avoid repeating the earlier leak.
- `order_details_page.dart`: converted from `StatelessWidget` to
  `StatefulWidget`. Does **not** open its own channel — instead receives
  live updates from the list page via a `ValueListenable<Map<String,
  dynamic>>`, so an open details screen updates live without doubling the
  channel count for that user.
- `notification_service.dart`: added `'orders'` → `NotificationEvent
  .orderDelivered` route mapping (previously fell through to `general` and
  was invisible to any order screen) — used as a secondary refresh trigger
  alongside push notifications, independent of whether the user granted
  notification permission.

**Database change required (and applied):**
```sql
alter publication supabase_realtime add table order_tracking;
```
`orders`, `subscription_daily_orders`, and `users` were already in the
publication (from 2026-07-02); `order_tracking` was missing, which caused
the entire channel's subscribe to fail silently — not just the tracking
listener, but the co-located `orders` listener on the same channel too.
This is why orders weren't appearing even though `orders` itself was
already published.

**Files changed:** `lib/screens/orders/order_page.dart`,
`lib/screens/orders/order_details_page.dart`,
`lib/services/notification_service.dart`,
`lib/services/order_service.dart` (added then later removed
`getRawOrderFuture`, no longer needed once the details page stopped
fetching independently)

### 2. Realtime Channel Consolidation (Capacity)

Supabase's concurrent-connection quota counts **channels**, not
WebSockets — multiple channels from the same app instance each count
separately (Free: 200, Pro: 500, Pro no-cap: 10,000). The app was holding
up to 4 channels per active user (app-wide `users` stream, a duplicate
`users` stream inside the subscription page's wallet listener, the orders
list channel, and the order-details channel).

**Fix — reduced to at most 2 channels per user:**
- `subscription_page.dart`: removed `_setupWalletListener()`, which opened
  a second realtime stream on the same `users` row that the app-wide
  `userDataProvider` already streams. `_walletBalance` is now a getter
  reading the shared provider. Nothing in `build()` depended on the removed
  field, so no UI reactivity was lost.
- `order_details_page.dart`: removed its per-order channel entirely (see
  item 1 above) — it now receives updates from the orders list page's
  existing subscription instead of opening a duplicate one.
- `order_service.dart`: removed the now-unused `getRawOrderFuture()`.

**Net effect:** ~92–242 concurrent users supported on Free/Pro plans
(alongside 10–15 admin sessions) at 2 channels/user, versus roughly half
that before.

**Files changed:** `lib/screens/subscription/subscription_page.dart`,
`lib/screens/orders/order_details_page.dart`,
`lib/screens/orders/order_page.dart`, `lib/services/order_service.dart`

### 3. Loading States: Spinners → Shimmer (App-Wide)

Home page showed a full-page skeleton, then dropped into a second wave of
individual spinners for category images, best-seller thumbnails, and the
subscription calendar — a visible two-phase loading flicker. Root cause was
an `&&` gate (`isLoading = userData.isLoading && categories.isLoading &&
bestSellers.isLoading`) that dropped the skeleton the instant the *fastest*
of three providers resolved, leaving the slower sections to fall back to
their own spinners.

Extended the same shimmer treatment to every content-loading spinner
across the app (buttons/overlays showing genuine in-flight action feedback
— Place Order, payment verification, save/delete confirmations — were
deliberately left as spinners, since a spinner correctly represents "your
tap is being processed" in a way shimmer would misrepresent).

**New shared widgets in `lib/widgets/shimmer_placeholders.dart`:**
`ShimmerBox`, `ShimmerCircle`, `CategoryGridSkeleton`,
`BestSellerRowSkeleton`, `ProductGridSkeleton`, `ProductCardSkeleton`,
`ListRowsSkeleton`, `InlineShimmer`, `TransactionTileSkeleton`,
`TransactionListSkeleton`, `StatCardSkeleton`, `OrderCardSkeleton`,
`OrdersPageSkeleton`, `SubscriptionSkeleton` (see item 4/5/6 below for the
wallet, orders, and subscription rebuilds specifically).

**Screens converted:** `home_page.dart` (removed the `&&` gate entirely —
each section now owns its own shimmer, no full-page skeleton swap),
`Allproducts/allproducts_page.dart`, `cached_product_image.dart` (default
placeholder, covers product images app-wide), `cart_page.dart`,
`checkout.dart`, `walletpage.dart` (initial pass — see item 4 for the
follow-up rebuild), `manage_addresses_screen.dart`,
`select_address_page.dart`, `notifications_page.dart`,
`subscription_list_page.dart`, `pause_management_page.dart`,
`subscription_day.dart`, `create_subscription_page.dart`,
`subscription_address_page.dart`, `product_details_page.dart`,
`order_page.dart` (FutureBuilder waiting state).

### 4. Wallet Page Loading State Rebuilt to Match Real Layout

The wallet page's loading state replaced the **entire body** — including
the always-static brown balance banner, "Add Money" button, and
"Transaction History" header — with a generic `ListRowsSkeleton` (5
identical grey blocks unrelated to the real layout).

**Fix:**
- Balance banner, "Available Balance" label, and Add Money button now
  render immediately and permanently. Only the ₹ balance figure and the
  "₹X/day avg · N days left" pill show a shimmer sized to their real
  dimensions while wallet data loads.
- Added a dedicated `isLoadingTransactions` flag, separate from the
  balance's `isLoading` — previously an empty transaction list during load
  was indistinguishable from a genuinely empty wallet ("No transactions
  yet").
- New `TransactionTileSkeleton` / `TransactionListSkeleton` mirror
  `TransactionTile`'s real layout (avatar circle, title, subtitle, date,
  trailing amount).

**Files changed:** `lib/screens/wallet/walletpage.dart`,
`lib/widgets/shimmer_placeholders.dart`

### 5. Orders Page Loading State Rebuilt to Match Real Layout

Same issue as the wallet page: the `FutureBuilder`'s waiting state was a
bare `ListRowsSkeleton`, hiding the stat cards and order cards behind
generic bars with no resemblance to their real shapes.

**Fix:**
- `StatCardSkeleton` mirrors `_StatCard`'s exact 104px height, small label
  line above a large value line.
- `OrderCardSkeleton` mirrors `_OrderCard`'s real structure: header row
  (order id + date lines, status pill), a row of two 48×48 thumbnail-shaped
  blocks with a trailing total placeholder, and a footer row with a
  divider.
- `OrdersPageSkeleton` composes both into the real page's layout order.
- Filter tabs (All/Active/Delivered/Cancelled) were deliberately **not**
  shown during the loading state — they act on order data that doesn't
  exist yet, so showing them as already-tappable above a skeleton list
  would be misleading.

**Files changed:** `lib/screens/orders/order_page.dart`,
`lib/widgets/shimmer_placeholders.dart`

Opening a subscription (from home or the subscriptions list) showed an
approximate skeleton — a plain status-card-sized rectangle, a bare weekday

and no action cards, so it didn't resemble the real page at all.

**Fix — `SubscriptionSkeleton` rebuilt to mirror all three real

- The AppBar was already unaffected by the loading gate (title falls back
  to "Subscription" before data loads), so no change was needed there.

### 7. "Buy Again" Wired Up on Delivered Orders

The "Buy Again" button shown on delivered order cards was a static
`Container` with no `onTap` — tapping it fell through to the card's own
tap handler and opened order details instead, which looked like (and
functionally was) a bug.

**Fix:** re-fetches each item's *current* product and variant via
`ProductService().getProductById()` rather than trusting the order's frozen
snapshot fields (price, stock, and images are fixed at order time — a
product could have changed price, gone out of stock, or been discontinued
since). Adds available items to the cart at their live price; skips and
names any unavailable ones in a summary snackbar with a "View Cart"
shortcut. Shows a brief spinner in the button while adding, and guards
against double-tap.

Money and delivery-address logic were **not** touched — Buy Again only adds
items to the shared cart; checkout's existing delivery-charge quoting,
wallet-affordability check, and address-serviceability check (all of which
already existed and apply to any cart item regardless of origin) run
unchanged. The delivery address used is whatever the customer is currently
browsing under, not the original order's address — this is the standard
"reorder" pattern (matches Amazon/Swiggy-style behavior) and was a
deliberate choice, not an oversight.

**Files changed:** `lib/screens/orders/order_page.dart`

### 8. "Write Review" Made Actually Visible

The per-item "Write Review" button (shown on delivered order items in
order details) was 10px text on a 5%-opacity background with no icon or
border — effectively invisible; it read as a faint label, not a button,
which is why it went unnoticed without being told exactly where to look.

**Fix:**
- Button is now a filled, icon-labelled chip (star icon + 13px bold white
  text on the primary color).
- The "Items in Order" section title becomes "Items in Order — Rate them
  below" for delivered orders, so the section explains the buttons' purpose
  instead of relying on the button alone to be self-explanatory.
- Kept the action per-item (not a single order-level button), since an
  order can contain multiple products each needing its own rating.

**Files changed:** `lib/screens/orders/order_details_page.dart`

### 9. Live Visual Feedback on the Add/Edit Address Save Button

The Save button (Add Address / Update Address) looked and behaved
identically regardless of form completeness — the only feedback on an
incomplete form was red validator text appearing after the button was
tapped. There was also no loading indicator while the save request was in
flight. This screen (`add_edit_address_screen.dart`) is shared by every
address entry point in the app — home page, manage addresses, select
address, and both subscription creation/address screens — so the fix
applies everywhere at once.

**Fix:**
- Live validity tracking via listeners on the required text controllers
  plus the state dropdown's `onChanged`, recomputed on every
  keystroke/selection.
- Button is filled and enabled (primary green, elevated) once name, phone
  (10 digits), address line 1, city, state, and pincode (6 digits) are all
  valid; dimmed and disabled (grey, flat) while incomplete, with a short
  hint line explaining why.
- Save now shows a spinner in the button while the request is in flight,
  and guards against double-submission.

**Files changed:** `lib/screens/address/add_edit_address_screen.dart`

## Admin Panel (Hetha_admin)

### 10. Subscription Eligibility Toggles Added to Product Form

`products.is_default_sub` / `is_additional_sub` gate whether a product
appears at all in the customer app's subscription product picker
(`create_subscription_page.dart` filters to `defaultSub || additionalSub`),
but neither column was exposed anywhere in the admin panel — no checkbox in
the form, no field in the save payload, no handling in the API route. Both
default to `false` in the schema, so every product was invisible to
subscriptions unless the flag was flipped directly in the database — which
is how the one product that did appear (Ghee) became eligible while the
other three products did not.

**Fix:**
- `lib/types.ts`: added both fields to the `Product` interface.
- `ProductForm.tsx`: two new Status checkboxes — "Subscription (default)"
  and "Subscription (add-on)" — wired into `formData` with the same pattern
  as the existing `in_stock`/`is_bestseller` flags, initialized from
  `productToEdit` when editing.
- `app/api/admin/products/route.ts`: POST (insert) and PUT (update) both
  now accept and persist `is_default_sub`/`is_additional_sub`.

No `select`-side changes were needed — `productService.ts` already selects
`*` on `products`.

**What the two flags mean (for future reference):**
- `is_default_sub` — marks a product as one the subscription flow
  *requires*: `create_subscription_page.dart` blocks subscription creation
  unless at least one selected product has this flag ("Please select at
  least one default product (milk)"). Intended for daily-essential items a
  subscription doesn't make sense without.
- `is_additional_sub` — marks a product as an *optional* add-on selectable
  within a subscription, with no such requirement attached.
- Only visual difference in the picker today: `is_default_sub` products get
  a green "Essential" badge; `is_additional_sub` products get no badge at
  all. Product list ordering in the picker is `.order('id', ascending:
  true)` — sorted by the product's UUID, which is **not** chronological by
  creation date or by when a flag was set (UUIDs are random). Noted as a
  possible follow-up if a more deliberate order (e.g. default-first, then
  alphabetical) is wanted later — not yet implemented.

**Files changed:** `lib/types.ts`, `app/admin/products/ProductForm.tsx`,
`app/api/admin/products/route.ts`
