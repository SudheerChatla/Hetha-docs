## 12. Subscription Wallet Check — 3-Day Buffer for All Subscriptions

**File:** `lib/screens/subscription/create_subscription_page.dart`

Upgraded the Phase 3 wallet check. Previously it only required one day of the new subscription's cost. Now it requires a **3-day buffer of the TOTAL daily commitment** (all existing active subscriptions + the new one).

**Logic:**
```
existingCommitment = get_user_daily_commitment(userId)   // RPC
totalDailyCommitment = existingCommitment + newSubDailyCost
required = totalDailyCommitment × 3
if walletBalance < required → block creation, ask to recharge
```

**Examples:**
- First subscription ₹100/day, wallet ₹250 → needs ₹300 → blocked
- Adding 2nd sub (₹50/day) to existing (₹100/day), wallet ₹400 → needs ₹450 (3 × ₹150) → blocked

Error message tells the user the exact amount needed. Gives the business a 3-day window to remind customers to recharge before deliveries are affected.

## 14. Full Razorpay Checkout Integration (Server-Verified)

**Files:**
- `lib/screens/checkout/checkout.dart`
- `supabase/functions/razorpay/index.ts`

### 14.1 Client Flow
- Razorpay instance set up in `initState`, disposed in `dispose`
- Selecting "Pay Online" → "Pay & Place Order":
  1. Calls `razorpay` edge function (`create-order`) to create a payment order for the order total
  2. Opens the Razorpay payment sheet (UPI/card/netbanking)
  3. On success → calls edge function `verify-order-payment` (server verifies + places order)
  4. On failure → shows error, no order placed
- `_pendingOrder` holds order context between opening the sheet and the success callback
- Button shows a spinner while payment is processing
- **Edge case handled:** if payment succeeds but order placement fails, shows a critical message with the payment ID for support follow-up

### 14.2 Edge Function — New `verify-order-payment` Action
Added to the existing `razorpay` edge function (wallet recharge logic left untouched):
1. Verifies the Razorpay signature server-side using HMAC-SHA256 (same logic as wallet recharge)
2. Only if valid → calls `place_order` RPC **server-side** with `payment_method: 'razorpay'`
3. Returns the order result

**Security:** Order placement now happens server-side, gated behind signature verification. A tampered client cannot fake a successful payment. The secret key never leaves the edge function.

### 14.3 Database Note
- Confirmed the 5-param `place_order` RPC handles `razorpay` correctly — only deducts wallet when `payment_method = 'wallet'`, sets `payment_status = 'pending'` for razorpay (no double-charge)
- Identified a duplicate old 4-param `place_order` function (oid 30671) that is safe to drop — all callers use the 5-param version

### 14.4 Deployment
- Edge function redeployed via Supabase dashboard (no `deno.json` change needed — uses existing imports)
- Still uses Razorpay **test key** (`rzp_test_...`) — switch to live key before production

## 15. Razorpay Security Hardening — Unified Server-Side Verification

**Files:**
- `lib/screens/wallet/walletpage.dart`
- `lib/screens/wallet/razorpaypayment.dart` (stale comment fixed)
- `supabase/functions/razorpay/index.ts`
- Database (functions dropped)

### 15.1 Problem Found
The wallet recharge verifier (`verify_razorpay_recharge` Postgres RPC) had the **Razorpay secret key hardcoded in plain text** inside the function body — visible to anyone with DB access.

### 15.2 Wallet Page Rewired
- `_handlePaymentSuccess` now verifies via the `razorpay` edge function (`verify-payment` action) instead of calling the hardcoded-secret RPC
- Added user-facing error snackbar on verification failure

### 15.3 Edge Function `verify-payment` Made Atomic
- Replaced the non-atomic read-then-write wallet update with a call to the `update_wallet_balance` RPC (row-locked via `FOR UPDATE` — prevents race conditions)
- Secret is read from the edge function env (`Deno.env.get('key_secret')`), never from the DB

### 15.4 Database Cleanup (dropped two functions)
```sql
DROP FUNCTION public.place_order(p_user_id uuid, p_address_id uuid, p_payment_method text, p_cart_items jsonb);
DROP FUNCTION public.verify_razorpay_recharge(uuid, numeric, text, text, text);
```
- Old 4-param `place_order` — superseded by the 5-param version (all callers pass delivery charge)
- `verify_razorpay_recharge` — replaced by edge function verification; removes the hardcoded secret from the database entirely

### 15.5 Result
- Razorpay secret now exists **only** in the encrypted edge function environment
- Both wallet recharge and checkout verify through the same secure edge function (2 invocations each: create-order + verify)
- Wallet credits are atomic

## 16. UTC → Local Timezone Fix (Wallet + Orders)

**Files:**
- `lib/screens/wallet/walletpage.dart`
- `lib/services/order_service.dart`

**Problem:** Supabase returns `created_at` / `placed_at` timestamps **without a timezone marker** (e.g., `2026-05-31T19:26:00`). The values are stored in UTC, but Dart's `DateTime.parse` treats a marker-less string as **local time** — so a 00:56 AM IST recharge displayed as "Yesterday, 19:26". Just calling `.toLocal()` didn't help because Dart already thought it was local.

**Fix:** Detect whether the timestamp string has a tz marker (`Z` or `+`). If not, append `Z` to explicitly mark it as UTC, then `.toLocal()` converts correctly to device time (IST).

- **Wallet page** — applied in `_fetchTransactionHistory`
- **Orders** — applied at the source in `_mapOrderData` (covers both the orders list and order details, since both read the mapped `date`)
- **Home calendar** — already correct (generates dates from `DateTime.now()`, never parses UTC strings)

**Note:** If timestamps are shown elsewhere (subscription pages, admin panel order dates), the same pattern may need applying. Admin panel uses JS `new Date()` which handles ISO tz strings differently — worth a check.
