## Launch blockers

These three prevent shipping at all. Each needs a decision or a credential that
isn't in the codebase.

### 1. App identity and release signing

**State.** `Hetha_app/android/app/build.gradle` still has the Flutter template
defaults: `applicationId = "com.example.frontend"`, and `buildTypes.release`
uses `signingConfig = signingConfigs.debug`. iOS is the same —
`PRODUCT_BUNDLE_IDENTIFIER = com.example.frontend` in
`ios/Runner.xcodeproj/project.pbxproj`.

**Why it blocks.** Google Play and the App Store both reject `com.example.*`
package names outright, and Play will not accept a build signed with a debug
key. Beyond that, the application id is permanent: once an app is published
under an id, it can never be changed — a rename means a new listing and losing
every existing install and review. So this has to be right before the first
upload, not after.

**Fix.** Choose the id (e.g. `in.hetha.app`), generate a release keystore, store
it outside the repo, and wire `key.properties` + a `signingConfigs.release`
block. The keystore must then be backed up somewhere durable: lose it and you
can never publish an update to that listing again.

**Needs from you.** The chosen id, and the keystore (generated by you so the
signing key is never in my hands or the repo).

### 2. Razorpay is still in test mode

**State.** The test key id `rzp_test_KCIGHsFejobevq` is hardcoded at
`lib/screens/checkout/checkout.dart:110` and
`lib/services/razorpay_payment_service.dart:19`. The matching
`key_id`/`key_secret` in the edge function environment are test credentials too.

**Why it blocks.** No real money can move. Test mode accepts fake cards and
settles nothing.

**Fix.** Swap both client sites and the edge function's `key_id`/`key_secret`
**together** — a live client key against a test secret (or vice versa) fails
signature verification on every payment. The key id is public and safe in the
client; the secret must stay only in the edge function environment.

**Needs from you.** Live Razorpay credentials, which requires a completed KYC on
the Razorpay account.

### 3. "Delete Account" deletes nothing

**State.** `lib/screens/profile/settings_page.dart:316` shows a confirmation
dialog headed "This action cannot be undone", and on confirm it navigates to
`/signin`. It deletes no data and does not even sign the user out. The comment at
line 344 acknowledges this and defers to support.

**Why it blocks.** Google Play policy requires an in-app route to request
account and data deletion for any app with accounts. A dialog that claims to
delete and doesn't is worse than no button — it is a false statement to the user
about their data, and it is the kind of thing that fails review.

**Fix — and this needs a product decision.** A literal hard delete conflicts with
the rest of the system: the user may hold a wallet balance you owe them, and
their order history is referenced by the money invariants added in migration 012.
The recommended shape is: deactivate the account immediately, record a deletion
request, surface it in the admin panel, and let staff settle any balance before
purging. That satisfies the policy (the user has a working in-app route) without
destroying financial records.

**Needs from you.** Which behaviour you want, and what happens to a non-zero
wallet balance on deletion.

## Fix before real customers

No external input needed for any of these.

### 4. No Razorpay webhook

**This is the only item where a customer following the rules still loses money.**

**State.** Settlement is entirely client-driven. The app posts
`{intent_id, order_id, payment_id, signature}` back to the `razorpay` edge
function, which then calls `finalize_wallet_topup` / `finalize_order_payment`.
If that post never happens, nothing settles.

**Why it matters.** Between Razorpay capturing the payment and the app posting
back, the app can die for entirely innocent reasons: the customer backgrounds
it, the network drops, the battery dies, Android kills it for memory. Razorpay
has the money; the intent stays `created`; there is no order and no wallet
credit. The customer is out of pocket through no fault of their own, and the
first you hear of it is a support call. Every other risk on this list is either
an attacker or an inconvenience; this one is ordinary behaviour producing a
wronged customer.

**Fix.** Add a `payment.captured` webhook that calls the same `finalize_*` RPCs.
They are already idempotent per `razorpay_payment_id` (migration 008), so the
webhook and the client callback can both fire safely — whichever arrives first
settles, the second is a no-op. No redesign required; this is additive.

### 5. No crash reporting

**State.** `pubspec.yaml` has `firebase_core` and `firebase_messaging` but no
crash reporter. Neither `FlutterError.onError` nor
`PlatformDispatcher.instance.onError` is wired anywhere in `lib/` — both error
channels currently discard everything.

**Why it matters.** When the app crashes on a customer's phone, the stack trace
is written to that device's log and lost. You have no idea it happened, how many
users hit it, or which devices and OS versions are affected. Your only signal is
a customer who bothers to call. That is tolerable for a content app; it is not
for a prepaid wallet business where the interesting crashes happen next to money.
It also compounds item 4: the payment window produces rare, device-specific
failures that can only be found as a pattern across many users.

**Fix.** Add `firebase_crashlytics` and wire both hooks in `main.dart`. Two hooks,
not one: `FlutterError.onError` receives errors Flutter itself catches (a widget
failing to build), while `PlatformDispatcher.instance.onError` receives errors
outside Flutter's reach (an async callback failing after navigation). Wire only
the first and a whole category still vanishes silently.

**Already in place.** The Firebase project exists, and both platform config files
(`android/app/google-services.json`, `ios/Runner/GoogleService-Info.plist`) are
on disk — correctly gitignored. So this is one package plus roughly ten lines.

`lib/utils/app_logger.dart` was written as the intended funnel for this; forward
non-fatal errors from `logDebug` rather than scattering reporter calls.

### 6. Expiry timers that nothing reads

**State.** Two 30-minute windows are recorded and never enforced:

- `payment_intents.expires_at` defaults to `now() + 30 minutes`
  (`docs/db/migrations/008_payment_intents.sql:39`).
- `place_order` stamps `orders.payment_pending_expires_at = now() + 30 minutes`
  (`007_money_integrity.sql:494`).

Searching every SQL file under `docs/db`, `expires_at` appears only in the table
definition and `payment_pending_expires_at` only where it is written. Settlement
gates on `status = 'created'` and never on expiry. Two further clues that this
was designed and left unfinished: the `payment_intents.status` CHECK permits
`'expired'`, a value nothing in the system ever writes; and `indexes.sql:71`
defines `idx_orders_pending_expires` on `payment_pending_expires_at WHERE
payment_status = 'pending'` — a partial index built to make the sweep query fast,
for a query that was never written.

**Why it matters, two ways.**

*Protection you believe you have.* The 30-minute limit is part of guarding
against a stale payment settling long after the fact. In practice an intent from
three days ago is as settleable as one from a minute ago. To be fair this is a
weakening rather than an open hole — payment ids are unique and settlement is
idempotent, so no replay for repeat credit is possible — but a control you think
you have and don't is worse than one you know you lack.

*Data you will feel sooner.* Every abandoned checkout leaves an order stuck in
`payment_pending` permanently. Staff see phantom orders that were never paid and
never will be, and every figure computed off the orders table — orders today,
conversion, revenue — drifts upward with junk indistinguishable from real
abandoned business.

**Fix, in two halves — both needed.** A scheduled job (Supabase cron, every ~15
minutes) that marks intents and pending orders past their expiry as expired; plus
one extra condition in the settlement functions so an already-expired intent is
refused. Without the second half, a payment arriving three days late still
settles whenever the sweeper hasn't happened to run yet.

### 7. Serviceability, cutoff and frequency are client-only

**State.** Three logistics rules are enforced only in the Flutter app:

- `delivery_area_service.dart:56` requests active areas only; line 283 checks the
  cutoff for tomorrow's order.
- `subscription_page.dart:443-448` splits `"16:30"` and compares it against the
  phone's clock in Dart.
- `subscription_address_page.dart` greys out addresses labelled
  "Not serviceable".

The database does not re-check. `place_order` copies the address pincode into the
order for history but never asks whether that pincode maps to a servable area.
`create_subscription_core` does look up `area_id` from the pincode, but it is
written as *if an area was found, snapshot its name and frequency* — on a miss it
proceeds with a NULL area instead of refusing, so the lookup exists in shape but
not in effect. `delivery_areas.order_cutoff_time` and `cancellation_cutoff_time`
are read by no SQL anywhere; they are columns the admin panel lets staff set and
no server code consults.

**Why it matters.** This is the same trust problem the 2026-07-28 audit closed
for pricing, applied to logistics — and it is the last one of its kind. A
modified build, a stale build, or a plain bug can create an order for a pincode
no route covers or after planning is done. There is also a subtler issue: the
cutoff is judged by the *phone's* clock, so a device with a wrong time zone or a
manually changed clock passes a check it should fail, with no bad intent
involved. The server has one clock, and it is yours.

The loss is operational rather than financial: a delivery lands on a run sheet
nobody can fulfil, discovered next morning, costing a phone call, an apology and
a refund.

**Fix.** In `place_order`, look up the pincode's area, refuse when missing or
inactive, and compare server time against `order_cutoff_time`. Same in
`create_subscription`. Keep the client checks — they exist to give a friendly
message before the customer wastes effort; the server's job is to be the gate
that cannot be talked out of it. Note the schema spells the column
`delivary_frequency` (pre-existing typo) — match it.

### 8. No CI

**State.** No `.github` directory in any of the three repos. All three gates pass
today only because they were run by hand.

**Why it matters.** The 41-assertion money suite guards against bugs that cannot
be seen by reading code — a database permission left quietly open. There is
already proof from this project's own history: migration
`010_grant_hardening.sql` exists *because* a privilege regression slipped past a
manual check, and the harness had to be taught to catch that whole class. That
lesson only stays learned if the harness actually runs. A test nobody runs
provides zero protection while feeling like insurance.

A second benefit: CI starts from an empty machine with only what is committed, so
it proves the project builds from the repository alone. Concretely, this project
would fail such a check today — `android/app/google-services.json` exists locally
but is gitignored, so a CI Android build cannot succeed as-is. Better to learn
that from a robot than from a second developer's laptop.

**Fix.** A workflow per repo, since the code lives in three places:
`docs/db/tests` verify in **Hetha-docs**, `flutter analyze` in **Hetha_app**,
`tsc --noEmit` + `lint` + `build` in **Hetha_admin**. The first two need no
configuration. The admin build may need the two `NEXT_PUBLIC_SUPABASE_*` values
as repository secrets — those are the public values already shipped to browsers,
not the service-role key, which must never go into CI.

**Caveat, stated honestly.** CI finds no new bugs by itself; it only guarantees
the checks you already have keep running. Its value therefore equals the value of
your tests: high for money paths, zero for UI, because there are no UI tests.

## Structural gap: no application tests

`Hetha_app` has no `test/` directory. `Hetha_admin` has no test suite. The DB
money suite is the only executable check on behaviour, and it covers the database
alone — nothing exercises checkout, subscription creation, the run-sheet
generator, or any admin screen.

This is why the fixes shipped today are verified by typecheck, analyzer and build
rather than by execution, and why the two new fail-closed throws in
`accessControlService.ts` have no test proving they fire. Worth setting up
`flutter_test` widget tests for checkout and subscription creation, and a
component/API test for the admin panel, before the surface grows further.
