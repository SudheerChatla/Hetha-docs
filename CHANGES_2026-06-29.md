# CHANGES — 2026-06-29

## Customer App (Hetha_app)

### 1. Wallet Page — Accurate "Days Left" Simulation

**Problem:** The wallet page showed "₹17500/day · 5 days left" by dividing wallet balance by the total subscription cost — but this was wrong for users with mixed delivery frequencies (daily + alternate day). It treated every subscription as if it delivers daily, overstating the daily cost and understating days left.

**Solution:** Replaced the simple division with a **day-by-day forward simulation**:

1. Fetches all active subscriptions with their `delivary_frequency`, `start_date`, and item costs
2. For each day (up to 90 days forward), checks which subscriptions actually deliver based on:
   - `frequency == 1` → delivers every day
   - `frequency > 1` → delivers only when `(daysSince(start_date) % frequency) == 0`
3. Sums the cost for that day, subtracts from balance
4. Stops when balance can't cover a day's deliveries
5. Calculates 7-day average for the "₹X/day avg" display

**Display changed from:**
```
₹17500/day · 5 days left
```

**To:**
```
₹10714/day avg · 11 days left
```

**Notes:**
- Does NOT account for pauses (conservative — shows fewer days than actual, which is fine)
- Does NOT change the 3-day buffer rule for subscription creation (that still uses the old conservative RPC)
- No new API/RPC needed — calculated client-side from subscription data already fetched
- Simulation runs in microseconds (max 5 subs × 90 days = 450 iterations)

**File modified:** `lib/screens/wallet/walletpage.dart`

### 2. Subscription Calendar — Correct Delivery Area Per Subscription

**Problem:** The subscription page always loaded the **first subscription's** delivery area (Ghaziabad, daily) regardless of which subscription was being viewed. So the Delhi/Noida (alternate day) subscription calendars showed green dots on every day instead of alternate days.

**Root cause:** `_loadUserAreaAndPincode()` called `getCurrentSubscription()` which returns the first active subscription, not the one currently being viewed.

**Fix:** When `subscriptionId` is provided (i.e., user tapped a specific subscription), load that subscription's `snapshot_pincode` and `delivary_area` directly from the database instead of using the generic first subscription.

**File modified:** `lib/screens/subscription/subscription_page.dart`

### 3. Subscription Calendar — "Completed Order" Fix

**Problem:** Tapping any past date showed "Completed Order" / "Delivery completed" regardless of whether the delivery was actually marked as delivered in the admin panel. Orders still showing "pending" in admin appeared as "completed" in the app.

**Root cause (two locations):**

1. `subscription_day.dart`: `isPastOrder = widget.day.isBefore(today)` — purely date-based, ignored actual status
2. `subscription_page.dart`: `_showPastDateDetails()` had a catch-all `else` branch that defaulted to "Delivery completed" for any subscribed + non-paused + delivery-available past day

**Fix:**
1. `subscription_day.dart`: Now checks `_existingDailyOrder!['status'] == 'delivered'` — only shows "Completed Order" when admin actually marked it delivered
2. `subscription_page.dart`: Past date dialog now shows status based on actual `subscription_daily_orders.status`:
   - `'delivered'` → "Delivery completed" (green)
   - `'pending'` → "Delivery pending" (amber)
   - `'skipped'`/`'cancelled'` → "Delivery skipped/cancelled" (red)
   - No record → "Scheduled (not tracked)" (grey)

**Files modified:** `lib/screens/subscription/subscription_page.dart`, `lib/screens/subscription/subscription_day.dart`

### 4. Subscription Calendar — Product Variant ID Matching Fix

**Problem:** Terminal showed `WARNING: SubscriptionEligibleProduct not found for ID: 50c77867-...` for every subscription product. The calendar's "Selected Products" section was empty even though products existed.

**Root cause:** `subscription_items` stores `variant_id` (e.g., the 1L variant UUID), but the lookup function `_findSubscriptionEligibleProductById()` was comparing it against `SubscriptionEligibleProduct.id` which is the **product** UUID (not variant). They never matched.

**Fix:** Updated the lookup to search within each product's `variants` list for a matching variant ID, not just the top-level product ID.

**File modified:** `lib/screens/subscription/subscription_page.dart`

---

### 5. Subscription Calendar — Status-Aware Dot Colors

**Problem:** All past dates with a `subscription_daily_orders` record showed the same orange dot ("Modified"), regardless of whether the delivery was completed, pending, or skipped.

**Fix:** Dot color now reflects actual delivery status:
- 🟢 Green → future scheduled delivery
- 🔵 Blue → past, delivered
- 🟠 Orange → past, pending (generated but not reconciled)
- ⚫ Grey → past, skipped or cancelled
- ⚪ Light grey → paused
- No dot → no record (before system was active)

**File modified:** `lib/screens/subscription/subscription_page.dart`

### 6. Subscription Calendar — Past Date Detail Dialog

**Previous behavior:** Tapping a past date showed a dialog saying "Had custom modifications" with no useful detail.

**New behavior:** Tapping a past date with a delivery record shows:
- Status (Delivered / Pending / Skipped)
- **Items list** with product name and quantity (e.g., "Gir Cow A2 Bilona Ghee ×1")
- **Amount deducted** (₹X)

Added `status` and `totalValue` fields to the `DailyOrder` model to support this.

**File modified:** `lib/screens/subscription/subscription_page.dart`
