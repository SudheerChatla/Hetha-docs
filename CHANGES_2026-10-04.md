  `node_modules/next/dist/docs/` before writing admin code.

  keys for each app.

  files when the two disagree. Each new migration must be appended to the
  hard-coded list in `verify_money_integrity.mjs`, then `DATA_MODEL.md`, the
  schema mirrors and the types updated.
- **Money rules.** Clients send ids and quantities and the DB decides money;
  the `internal` schema; deferred totals triggers and the
  `hetha.skip_money_checks` switch; delivery-charge rule; 3-day wallet buffer;
  `snapshot_*` columns.
- **Change-log format** (this file) and `REMAINING_FIXES.md`.

## 3. Realtime & scalability review

### Where Realtime is used

| Where | Listens to | Lives for |
|---|---|---|
| App, `lib/providers/user_provider.dart` → `UserService.streamUserData` | the customer's own `users` row (wallet, profile), filtered by id | the whole logged-in session |
| App, `lib/screens/orders/order_page.dart` | `orders` filtered by `user_id`, and `order_tracking` **unfiltered** (one channel) | only while the Orders screen is open |
| Admin, `app/admin/orders/page.tsx` | new `orders` inserts | while the page is open |
| Admin, `app/admin/daily-ops/hooks/useDailyOps.ts`, `hooks/useRealtimeSubscription.ts` | daily-ops changes | while the page is open |

Supabase limits **connections** (one WebSocket per device), not channels. One
phone = one connection, however many channels it has.

### What is managed correctly ✅
- `supabase_flutter` 2.12.4 disconnects Realtime when the app goes to the
  background and reconnects on resume, so idle phones don't count.
- The Orders screen removes its channel on every `dispose`. The leak that once
  caused `RealtimeSubscribeException` timeouts is fixed.
- The order details page reuses the Orders screen's feed instead of opening its
  own channel.
- Updates missed in the background are covered by a refresh on resume (away
  for more than 20 s).
- 400 ms debounce; fetches never overlap; order list capped at 50
  (`order_service.dart:17`).
- On logout the user stream switches to null, so the old stream is cancelled.
- Admin panel removes every channel on unmount; few staff, so negligible.

### Issue found ⚠️ → fixed in §4
The `order_tracking` listener had no filter. See §4 for the explanation,
example and fix.

### Capacity
Supabase plan limits as published (confirm on their pricing page; not checked
live):

| Plan | Concurrent connections | Messages / month |
|---|---|---|
| Free | 200 | 2M |
| Pro | 500 by default, can be raised (up to about 10,000) | 5M, then pay per use |

Assuming 2–5% of customers have the app open at the busiest moment:
- **Free:** fine up to about 4,000–5,000 customers, with no margin.
- **Pro at 500:** roughly 10,000–25,000 customers.
- **Beyond that:** raise the connection limit; no code change needed.

Message volume is low, since each customer only receives their own updates.

### Verdict
Scalable for a regional delivery business up to tens of thousands of
customers, once §4 is live and production is on the Pro plan.

**⚠️ Not checked yet:** how fast the heavy DB functions are at volume (daily
run generation, bulk daily-order edits, daily wallet deductions) and the DB
compute size. No load test has been done. If 10,000+ customers are expected,
test daily-run generation against a few thousand subscriptions.

At much larger scale, the next step would be Supabase **Broadcast** (a DB
trigger sends each change to a private per-user channel). Not needed now.

## 4. Fix: unfiltered `order_tracking` listener (migration 035)

### Problem
`Hetha_app/lib/screens/orders/order_page.dart` listened to **every**
`order_tracking` change in the system, because the table had no `user_id`
column to filter on. Supabase must not send a customer someone else's row, so
for each change it ran the table's RLS SELECT policy (`docs/db/policies.sql:152`,
an `EXISTS` lookup into `orders`) once **per connected subscriber**, just to
find the one customer allowed to see it.

### Example
7 AM: 300 customers on the Orders screen; staff update tracking for 400 orders.

| | Should be | Was |
|---|---|---|
| RLS checks per tracking change | 1 (the owner) | 300 (everyone on the screen) |
| Total for the morning | 400 | **120,000** |
| Customers notified | 400 owners | 400 owners (same) |

Invisible in testing with 2–3 users. At scale, Realtime processes the checks
one at a time, so updates arrive late; the checks also load the database. The
cost grows with customers online × tracking changes.

### Why the listener could not just be removed
Staff can save courier / AWB / customer message **on its own**, without
changing the order status (`Hetha_admin/app/api/admin/orders/[id]/route.ts`).
Then only `order_tracking` changes, not `orders`. Removing the listener would
stop customers seeing those details live. (An earlier suggestion in this
session to remove it was withdrawn for this reason.)

### Fix

| Piece | What it does |
|---|---|
| `order_tracking.user_id` | New nullable `uuid` column (like the order's owner), backfilled from `orders.user_id` |
| `internal.set_order_tracking_user_id()` + `trg_set_order_tracking_user_id` | BEFORE INSERT OR UPDATE on `order_tracking`: always sets `user_id` from the order; any supplied value is overwritten |
| `internal.sync_order_tracking_user_id()` + `trg_sync_order_tracking_user_id` | AFTER UPDATE on `orders`, only WHEN `user_id` changed: tracking rows follow the new owner |
| App listener (`order_page.dart`) | `filter: user_id = eq.<own id>`, same as the `orders` listener; comments updated to explain why |

Result: each tracking change is RLS-checked for exactly one subscriber. In the
example, 120,000 checks → 400, flat however many customers are online.

### Design decisions
- **Owner changes are covered.** `claim_adhoc_user` (ad-hoc → app user)
  rewrites `users.id`; live FKs carry it to `orders.user_id` via
  `ON UPDATE CASCADE` (per `DATA_MODEL.md`; `schema.sql` doesn't show the
  cascade). The AFTER trigger on `orders` fires for that cascaded update, and
  the BEFORE trigger then re-reads the already-updated order, so both agree.
- **Triggers, not an FK, on the new column.** An FK cascade from `users` could
  run before or after the cascade to `orders`, so the order of updates is not
  guaranteed. Deriving the value from the order avoids that.
- **Nobody writes the column.** The admin panel and `place_order_core`
  (`functions_internal.sql:1110`) are unchanged; the database fills it in.
- **RLS unchanged.** Policies still authorise through `orders`. A wrong
  `user_id` could only stop a live update, never leak a row.
- **Trigger functions** live in the `internal` schema, are `SECURITY DEFINER`
  with pinned `search_path` (same as migration 033), and have EXECUTE revoked
  from `PUBLIC`, `anon`, `authenticated`.
- **Idempotent.** `ADD COLUMN IF NOT EXISTS`, `CREATE OR REPLACE`,
  `DROP TRIGGER IF EXISTS`; safe to run twice.
- **No index added.** Realtime filters are evaluated on the change record, not
  through an index.
- **DELETE events** can't be filtered by Realtime. Checked: nothing in the app,
  admin panel or DB functions deletes `order_tracking` rows.
- **Old app builds** are unaffected: they don't filter, and an extra column is
  harmless.

## 5. Test suite: calendar-dependent dates fixed

**Problem.** Checks 8r–8r3 (`reschedule_order`, migration 034) used fixed
dates `2026-10-02`, `2026-10-05` and `2026-12-25`. `reschedule_order` refuses
past dates, so from 2026-10-03 the suite **crashed** at 8r2 and never reached
later sections. `2026-12-25` would have broken after Christmas.

**Fix.** They now compute dates from `internal.today_ist()` with the same
cadence logic:
- 8r: today + 30.
- 8r2/8r3: a future delivery day D for the alternate-day test area
  (reference 2026-10-01). A request for D+1 must snap to D+2; D+4 is kept.

The pure `next_delivery_date` checks (8g–8i) don't depend on today and keep
their fixed dates.

## 9. Rollout for migration 035

1. ✅ Apply `035_order_tracking_user_id.sql` in the Supabase SQL Editor,
   preferably at a quiet hour. The backfill sends one Realtime event per
   existing tracking row to old app builds on the Orders screen; each is
   debounced into a single refresh.
2. ✅ Run the verification queries at the bottom of the migration. Query 3
   (mismatches) must return 0; query 4 must list `user_id` for
   `order_tracking` in the `supabase_realtime` publication.
3. ⏳ Live smoke test with the new app build: customer A on the Orders screen.
   Save courier info on one of A's orders in the admin panel → A's list
   refreshes within a second or two. Save courier info on customer B's order →
   A's list does **not** refresh.
4. ⏳ Release the app build. Old builds keep working unchanged.

**Order matters.** Against a database without the column, Realtime refuses
the filtered subscription. Both listeners share one channel, so a new build
released first would most likely lose live `orders` updates too.

returned". Checks: the column existed, 0 mismatched rows, and the Realtime

**Second run: whole file re-run** in a fresh query tab with nothing selected
