## 2. "Edit multiple days" is now all-or-nothing (migration 027)

**Problem (two bugs):**
1. **Partial saves.** The app saved each selected day with its own server
   call. If day 6 of 10 failed (e.g. already finalized by ops), days 1–5 stayed
   saved, days 7–10 were never tried, and the customer saw one generic error
   with no idea which days had changed.
2. **Wallet check per day only.** Each call compared that one day's extra cost
   against the same, unchanged wallet balance (nothing is debited until the
   daily run is finalized). Raising 10 days in one go passed 10 checks that
   together only proved the wallet could cover **one** day's extra.

**Fix:**
- **Migration 027** (`docs/db/migrations/027_bulk_modify_daily_orders.sql`):
  new `public.modify_daily_orders_bulk(user, subscription, days)`.
  1. Checks **every** day first — ownership, not in the past, not finalized /
     delivered / paid, prices taken from the catalog.
  2. Checks the wallet **once**:
     `wallet ≥ 3 × daily commitment (all subscriptions) + SUM of every day's extra in this batch`.
  3. Only then writes all the days, in one transaction.
  A problem on any day leaves **every** day exactly as it was. A day with no
  items is reset to the default, same as the single-day screen.
- **App:** `SubscriptionService.saveDailyOrdersBulk()` sends the whole batch in
  one call; `bulk_modify_subscription.dart` uses it instead of the loop. On
  failure the message now says **no days were changed**.
- Single-day edits (`modify_daily_order`) are unchanged.

Example — daily commitment ₹280, three days each raised by ₹400:

| Wallet | Before | Now |
|---|---|---|
| ₹1,240 (enough for one day's extra) | all 3 saved | refused, nothing saved |
| ₹2,040 (3 × 280 + 3 × 400) | all 3 saved | all 3 saved |

**Decision recorded:** the check covers **only the days in one batch**. It does
not add up extras from earlier, separate edits — that would keep tightening
the requirement the further ahead a customer edits. The real safeguard stays
`finalize_daily_run`, which only debits what the wallet actually holds on the
day. A simpler rule ("just keep 3 days' worth, no extra-cost math") is being
discussed with the client — see *Open items*.

**Status:** ✅ 6 new tests. ⏳ on-device test.

## 3. Products can be archived; delete is safe (migration 028)

**Problems:**
1. **Delete could half-fail.** `DELETE /api/admin/products` deleted images, then
   variants, then the product, checking only the last step. A product with order
   history has variants the database won't let go of, so the delete failed —
   **after** the images were already gone.
2. **No way to retire a product.** Only `in_stock` existed, and the app shows
   out-of-stock products, so a discontinued product stayed visible for good.

**Fix — database (`028_product_archive_and_safe_delete.sql`):**
- New column **`products.is_archived`** (default `false`).
- Checkout, subscriptions and day edits **refuse archived products**
  (`internal.normalize_cart`) — even from an old app build still showing one.
- **`public.delete_product(id)`** — one transaction. Refuses if the product has
  any order, subscription, daily-delivery or review history, and says how much
  ("…has history (18 order line(s), …) … Archive it instead."). Otherwise
  removes cart rows, images, variants and the product together.
- **`public.set_product_archived(id, true|false)`** — archive / restore.
  Refused while an active subscription still delivers the product (it would
  keep being delivered and billed). Archiving also removes the product from
  customers' carts.
- Both need `products:edit` (or super admin); customers and anon are blocked.

**Fix — admin panel:**
- Products page: **Active / Archived** switch, an **Archive / Restore** button
  on every row, and an "Archived" badge.
- Delete goes through `delete_product`; its message is shown as-is.
- Every admin product picker (ad-hoc order, ad-hoc subscription, daily ops,
  subscriptions) hides archived products.

**Fix — customer app:** catalog, bestsellers and both subscription product
lists hide archived products. An archived product opened directly (e.g. from
order history) shows as unavailable.

**When to use which:**

| Situation | Action |
|---|---|
| Temporarily unavailable | "In Stock" off (still listed, can't be ordered) |
| Discontinued, has orders/subscriptions in the past | **Archive** |
| Created by mistake, never ordered | **Delete** |

**Status:** ✅ 12 tests. ⏳ admin: archive, restore, delete a product with and
without history.

## 5. Cancelling now removes that subscription's leftover orders (migration 030)

**Found while removing dead code.** After `cancel_subscription`, the app ran
`_cleanupFutureDataOnCancellation`, which deleted future daily orders and pauses
directly from the client. The database never allowed that (admin-only since
migration 009), so it **always failed silently**. Had it worked, it would have
deleted the orders of **all** the customer's subscriptions, not just the
cancelled one.

**The real gap it hid:** a day the customer had edited is kept by the run-sheet
generator no matter what, and `finalize_daily_run` bills every pending order on
the date. So an edited day **after** the cancellation date would still have
been **delivered and charged to the wallet**.

**Fix:**
- **`030_cancel_subscription_cleanup.sql`** — `cancel_subscription` now:
  - explicitly checks the caller owns the subscription (or is an admin);
  - deletes **that subscription's** pending, unpaid, not-yet-locked orders
    after the last delivery date — today for an immediate cancel, the end
    date for a scheduled one;
  - never touches other subscriptions, or finalized / delivered / paid days;
  - keeps pauses, so "Revert Cancellation" brings the schedule back as it was.
  Same inputs as before — no app change needed to benefit.
- **App:** the dead client-side clean-up and its two call sites were removed.

**Status:** ✅ 3 tests. ⏳ on-device: edit a day after the cancel date, cancel,
check the day is gone and other subscriptions are untouched.

## 10. Email verification and password reset use a 6-digit code

**Repo:** `Hetha_app` (`4e9c217`). No database, admin or Android/iOS changes.

**Problem:**
- **Sign-up:** the verification email had a link. The app passed no redirect,
  so Supabase used the Site URL, `https://hetha.in/`. The email *was*
  verified, but the customer landed on the website with no message and no
  idea they should go back to the app.
- **Forgot Password:** the reset link also went to hetha.in, and the app had
  **no screen to set a new password**, so a customer who forgot their
  password could not recover the account.

**Options considered:** a link that opens the app (deep link), a friendly
landing page on hetha.in, turning verification off, or an emailed code.
**Chosen: emailed code.**
- It works when the email is read on another device.
- It is not broken by email apps' built-in browsers or link scanners.
- It needs no Android/iOS link setup.
- Customers still end up with a verified email.
- It costs nothing: it is the same email, with the code (`{{ .Token }}`) in
  place of the link. Supabase generates, stores (hashed), expires,
  rate-limits and checks the code; the app only collects it.

**Now:**

| Flow | Before | Now |
|---|---|---|
| Sign up | Submit → "check your email" → link → hetha.in → back to app → sign in | Submit → code screen → type 6 digits → **signed in**, Home |
| Sign in (verified) | Email + password | **Unchanged** — no code |
| Sign in (never verified) | "Email not confirmed" error | Fresh code sent automatically → code screen → signed in |
| Sign up with an already-verified email | "Account created! Check your email" (no email ever came) | "An account with this email already exists. Please sign in, or use Forgot Password." |
| Forgot Password | Link → hetha.in → dead end | Email → **Send Code** → code screen → **Set a new password** → signed in |

**Code screen (`verify_email_page.dart`):**
- 6-digit field: digits only, number keyboard, submits on the 6th digit, and
  offers code autofill where the phone supports it.
- **Resend code** has a 60-second countdown; only the newest code works.
- **Wrong email? Go back** returns to the previous screen.
- Plain messages for a wrong or expired code, too many tries, and no internet.
- Screen readers announce errors.

**Set a new password (`reset_password_page.dart`):**
- Same rules as sign-up: 8+ characters, a capital letter and a number.
- Leaving without saving (✕ or back) **signs the user out**, so the old
  password keeps working.

**Shared (`services/auth_flow.dart`):** `completeSignIn()` runs the
`claim_adhoc_user` profile sync and push-token registration for password
sign-in, code verification and password reset alike, so all three end in the
same state. The unused link-based `sendPasswordResetEmail` wrapper was removed.
The existing Sign In / Sign Up layouts are unchanged; only the Forgot Password
popup wording changed ("Send Code").

**Supabase dashboard (to do — after the new build is installed):**

1. Authentication → Sign In / Providers → **Email**:
   - Confirm email: **on**
   - Email OTP Expiration: **600**
   - Email OTP Length: **6**
   - *(optional)* Minimum password length: 8
2. Authentication → Emails → Templates → **Confirm signup** and **Reset
   Password**: replace the link with `{{ .Token }}`. No `{{ .ConfirmationURL }}`
   should remain.
3. Before real customers sign up: connect your own **SMTP** provider (the
   built-in sender allows only a few emails per hour).

Order matters: switching the templates before the new build is installed
would leave the old build receiving codes it has no screen for.

**Status:** ✅ 11 new unit tests; `flutter test` 67 passed; `flutter analyze`
clean. ⏳ templates to change, on-device tests (checklist 13–21).

## 11. Signed out unexpectedly → back to Sign In

**Repo:** `Hetha_app` (`28f8422`).

**Problem:** at start-up, `AuthWrapper` decides between Home and Sign In and
keeps watching the session. But after a sign-in from the Sign In screen the app
replaces it with Home, so nothing was watching any more. If the session ended
while the app was open, the app stayed on Home and every screen just failed
(orders empty, wallet and cart errors) until the app was restarted. Ways a
session can end like that:
- the user was deleted or blocked in the dashboard;
- Supabase revoked the session;
- the token refresh failed.

Normal use was never affected.

**Fix:**
- New `services/session_watcher.dart`: one listener on the auth stream the app
  already uses, started in `main()`. On an **unexpected** sign-out it goes to
  Sign In from any screen and shows *"You've been signed out. Please sign in
  again."* Sign-in, the hourly token refresh and other events are ignored. No
  polling and no network calls, so there is no performance cost.
- New `signOutIntentionally()`: sign-outs the app starts itself tell the
  watcher first, so they keep their own navigation and don't get the message.
  These are:
  - the Logout button;
  - leaving "Set a new password";
  - the profile-collision case;
  - `SupabaseAuthService.signOut`.

  No screen calls `auth.signOut()` directly any more.
- The push token can't be removed at that moment (the session is already gone);
  `register_device_token` moves it to whoever signs in next on the phone.

**Status:** ✅ 4 new unit tests; `flutter test` 71 passed; `flutter analyze`
clean. ⏳ on-device (checklist 22–23).

## 12. Previous account's screens reachable with Back after switching accounts

**Repo:** `Hetha_app` (`b644497`).

**Reported (2026-09-29):**
1. Signed in as `sudheerchatla5@gmail.com`, then Logout.
2. Signed in with another account and tested a wallet recharge.
3. Pressing Back showed the **previous account's Wallet page and balance**.

Closing and reopening the app fixed it.

**Cause:** Profile can be opened **on top of** Home (tap the avatar), so the
screen stack was `[main screen (A), Profile]`.
1. Logout replaced only the **top** screen with Sign In, leaving
   `[main screen (A), Sign In]`.
2. The next sign-in did the same with Home, giving
   `[main screen (A), main screen (B)]`.
3. Back popped B and showed A's old main screen. Its tabs (Wallet, Orders…)
   are kept alive for fast switching and still held A's data.

This was stale screens in memory only, not a data leak: every fresh query is
limited to the signed-in user by the database rules.

**Fix:**

| Where | Before | Now |
|---|---|---|
| Profile → Logout | replaced the top screen | clears **every** screen, then Sign In |
| Sign in success | replaced the top screen | clears every screen, then Home |
| Settings → Delete Account | same problem | clears every screen |
| Selected tab | next account opened on the last account's tab | resets to **Home** when the account changes (not on a token refresh) |

The email-code, reset-password and signed-out-watcher paths (sections 10–11)
already cleared every screen.

**Status:** ✅ 2 new unit tests; `flutter test` 73 passed; `flutter analyze`

order number **or internal ID** contains the text. The internal ID is a
`uuid`, and Postgres can't do a "contains" (`ILIKE`) match on a `uuid`, so it
rejected the whole query. The page showed any failure as an empty list, so it
looked like "no match" instead of an error.

**Fix:**
- `services/orderService.ts`: partial match on the **order number** only; the
  internal ID is matched exactly, and only when a full UUID is pasted.
- `app/admin/orders/page.tsx`:
  - a failed load now shows **"Couldn't load orders"** with the reason, not
    "No orders found";
  - arriving from **Open** with exactly one match expands that order's
    details automatically;
  - the search placeholder says "Search by order number…" (customer names
    were never searched).

| Search | Before | Now |
|---|---|---|
| **Open** on `ORD-20260824144226-7277` | "No orders found" | that order, details open |
| Typing `7277` | "No orders found" | every order whose number contains 7277 |
| Any search, if the server fails | "No orders found" | "Couldn't load orders" + reason |
